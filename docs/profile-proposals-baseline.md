# Profile proposals, Stage 0 baseline

The source baseline is `KnowMe-app/main` at `bc99ca2bd48322569a38334b18225e7cb9a6a061`. This audit covers the current application and checked-in Firebase rules. The test added in this stage exercises legacy behavior.

## Architecture map

| Concern | New-profile draft | Overlay on an existing record |
| --- | --- | --- |
| Record | `multiData/profileMutations/{creatorUid}/{cardId}` stores full draft data, status, timestamps, revision and claim keys. A push key reserves the permanent card ID. Canonical nodes first appear on approval. | `multiData/edits/{cardId}/{editorUid}` stores one current field delta per editor and target. An overlay can also target an unpublished create draft today. |
| Field representation | The complete proposed profile is saved. Revisions use the overlay change builder to record per-field edits. | `{from,to}` represents a replacement or clear. `{added,removed}` preserves multiple values and supports legacy `add`. Preview applies changes in timestamp and UID order. Ordinary enrichment of found cards saves touched fields and adds to existing values. |
| Discovery | `multiData/profileMutationOwners/{cardId}` resolves a hit to its author. `multiData/profileIdentityClaims/{key}` reserves normalized contact identifiers. `searchId/{value}/{field}` links identifiers to the reserved ID. Duplicate detection warns on collision and leaves the existing claim with its holder. | `multiData/editsByEditor/{editorUid}/{cardId}` and a browser fallback discover the author's own overlays. Saves add proposed identifiers to the same `searchId`, using the target ID. `editsContributors/{cardId}` is a best-effort cleanup roster with no grant in the checked-in rules. It does not grant profile visibility. |
| Revision and history | `saveCreateProfileMutation` uses a transaction with an expected-revision check when supplied. Each save advances the revision. Publication changes status at the same draft revision. The unused return helper advances it. The save writes `multiData/profileMutationHistory/{cardId}` per field after the main write. Index, pointer and claim cleanup are separate. A history write can fail after the draft has committed. | The current layer is read and set without a revision check. `multiData/editsHistory/{cardId}` stores field changes and supports review of superseded values. Settlement can split a historical entry, retain unresolved values and remove settled entries. The current settlement path does not retain an approval audit event. |
| Canonical write | Admin publication waits for queued saves, acquires claims and checks the draft revision while transitioning to `publishing`. It synchronizes `searchId` and `searchKey`, then atomically writes applicable profile body fields and accepted status. It builds the `matchingCards` projection and bumps its revision afterward. Cleanup is best-effort. The Workspace passes draft base data so unrelated overlays stay pending. | Review operates on a field value. The queue applies the selected change to the latest loaded base, persists it and settles the selected layer value. `persistCanonicalCard` syncs `searchId` and selects the account or imported-card writer by ID format. A draft target is written back to its revisioned draft and journal. Create publication marks remaining overlays `adminOnly` best-effort. Own-layer reads and RTDB grants still permit the original editor to read their layer. |
| Removal | Admin hard delete releases claims, removes current search links and contributions, clears comments and history, and removes the mutation last. The client does not clear its owner pointer. Clearing fields is a save and keeps the draft history. Whole-draft return sets `private` in an exported helper without a UI caller. | Authors can delete their own current layers. Admin rejection settles individual values, with path-dependent history and search cleanup. Current and superseded per-value discard check canonical values and current layers before removing a search link. |

The canonical record is split across `matchingCards`, `profileDetails`, `profileContacts`, `profileWorkflow` and `profileTechnical`. Admin can create and edit canonical records directly in the admin workspace. The source-aware form tracks the create draft's author and revision, keeps private admin notes and marks separate, and prefers canonical nodes unless given an explicit draft source. ## Behavior matrix

“Own” means the signed-in UID owns the record, draft, or overlay named in the column. Record creator and unrelated reader are relationships that can apply to the ordinary roles. The matrix describes checked-in rules and UI, including differences between them.

| Intended parent (`ip`) | Yes | Known-point read and supported search | Own overlay | Same permissions as donor | Same permissions as donor |

Known-leaf reads and collection reads are separate grants. The app filters shareable queue entries to pending drafts and excludes empty draft data from ordinary search. The raw draft leaf rule grants signed-in reads independently of status. An ordinary foreign-card link into the create workspace depends on a shared list the rules deny. Exact search resolves via the owner pointer, and workspace search can open a foreign hit for a contribution. Canonical search and feed access apply separately, including donor's limited lookup, unpublished projections, hidden cards and liked-only audiences. Proposal authorization currently checks path-bound IDs, but update writes do not check target existence, target visibility or allowed fields. Create writes require a status and revision field but do not enforce their values or transitions. Overlay history appends require an existing overlay by that editor, while create history accepts authenticated self-attributed, shape-valid rows without a draft ownership check. ### Registered account self-service

`/my-profile` directly saves the signed-in account's canonical nodes for donor, surrogate, agency, intended parent, inspector and admin acting as account owners. The form checks that the Auth session still owns the profile, serializes saves, replays a separate UID-scoped pending edit queue, and updates relevant search keys and shared snapshots. Registration uses the same account persistence boundary. The owner also controls publication and audience, photos, programs, and supported revocable profile links. Matching routes the owner pencil back to `/my-profile`. Profile-link snapshots and delegated reaction/note access are separate from proposal contributors. ## Convergence and compatibility

- Both implementations already share field-difference logic, normalization, card identity, an asynchronous editor queue, `searchId` operations, attribution and historical field changes. Save coordination, permissions, revision enforcement, history storage and review orchestration are duplicated. Only create needs a reserved new card ID, an initial full profile and first canonical publication. An update needs a target card ID, changed fields and their original values. It must remain attached to that card in search and matching.
- Normalize legacy records in read-only adapters first. Keep the existing card/author identity and existing source metadata and URLs. Use one draft contract with separate canonical application operations. Treat overlays on unpublished create targets as legacy contributions dependent on the create draft. Keep them reviewable against the draft until publication or settlement, preserving the card ID, original editor, original change and residual values. Avoid turning them into independent cards or pointing canonical update logic at a noncanonical record.
- Preserve raw status and timestamps, revisions, author and actor, field/value change types, active and superseded history, partial settlement, current search/claim associations and local pending snapshots. Mark absent legacy revisions or base values as unknown. Preserve `/my-profile` direct writes and enforce canonical visibility separately from proposal access. Keep old readers and writers during adapter adoption and switch application of each proposal to a single authority at cutover.
- Make index removals reference-aware across canonical values and all still-valid proposals. Current and superseded per-value discard check canonical values and current layers. Other unresolved historical rows do not count as index references. Corrected acceptance, bulk operations, and client/account deletion have different cleanup coverage. Bulk overlay operations attempt a parent-level removal where rules grant writes at editor children. Inline current acceptance settles before persistence and can append a replacement. The dedicated queue preserves replacements and persists before settlement. Create publication attempts identity claims but does not use the returned conflict list as a separate duplicate gate. Create-workspace settlement handles values separately and does not perform per-value index cleanup. Cover these differences with emulator fixtures before changing their behavior.
- Exercise competing authors, stale autosaves and approvals, an interrupted multi-step write and repeated settlement. Legacy overlay writes have no revision guard and external changes can occur between reading a target, persisting it and settling a proposal. Local replay has no persisted base revision. Preserve search, history, notification deduplication and cleanup through a dry-run inventory, controlled cutover, and rollback while legacy data remains recoverable.

# Підготовка міграції пропозицій анкет

Інструмент працює офлайн з повним JSON-знімком кореня RTDB. Підготовлений
знімок додає `multiData/profileProposals` зі станом `staged` і
`activeWriter: legacy`. Чинні адаптери залишаються єдиним шляхом збереження
та розгляду. Клієнтські правила закривають підготовлений вузол. Джерело,
канонічні вузли, рішення, `searchId` і `searchKey` зберігаються у знімку.

## Локальна репетиція

Потрібні Node.js і залежності репозиторію. Для тесту використовуйте синтетичну
фікстуру нижче. Для санкціонованої інвентаризації потрібен повний консистентний
експорт RTDB, включно з `accountDeletions` та індексами. Сам звіт показує лише
кількості й контрольні суми. Повний знімок та артефакти містять приватні дані,
тому зберігайте їх поза репозиторієм у каталозі з доступом власника.

```bash
snapshot=scripts/fixtures/profileProposalMigration/legacy-export.json
bundle=$(mktemp -d)
npm run test:proposal-migration
npm run migrate:profile-proposals -- --snapshot "$snapshot"
npm run migrate:profile-proposals -- --snapshot "$snapshot" --apply --output "$bundle"
npm run migrate:profile-proposals -- --snapshot "$bundle/staged.json" --verify
npm run migrate:profile-proposals -- --snapshot "$snapshot" --apply --output "$bundle"
npm run migrate:profile-proposals -- --snapshot "$bundle/staged.json" --rollback --output "$bundle"
cmp "$snapshot" "$bundle/backup.json"
cmp "$snapshot" "$bundle/rolled-back.json"
```

- Сухий прогін обчислює звіт без файлових записів. Для вже підготовленого
  знімка `--verify` перебудовує очікуваний вузол і звіряє всі записи та
  контрольні суми. Перевірка відхиляє зміну джерела або підготовлених даних.
  Списки у форматах SDK `.val()` і `.exportVal()` звіряються за однаковими
  дочірніми ключами. Вихідний файл зберігає свою початкову форму й пріоритети.
- `--apply` спершу зберігає побайтову копію `backup.json`, далі атомарно
  створює `staged.json`. Файли мають режим `0600`. Повтор з того самого
  джерела відтворює перевірений результат і використовує наявні файли. Якщо
  процес зупинився після копії, та сама команда продовжує підготовку. Змінені
  результати або знімок з іншої спроби потребують окремого каталогу.
- `--rollback` приймає перевірений `staged.json` з його комплектом. Команда
  відтворює точний `backup.json` у `rolled-back.json`. Вона звіряє повний
  підготовлений знімок з резервною копією, включно з рештою кореня RTDB.
- Повний `staged.json` і `rolled-back.json` призначені для перевірки на
  ізольованій базі. Імпорт повного файлу в живу базу замінив би чужі записи.

## Відображення записів

| Джерело | Підготовлений результат |
| --- | --- |
| `profileMutations/{creator}/{card}` | Одна `create`-пропозиція з оригінальним або детермінованим legacy ID, зарезервованим ID анкети, даними, станом, ревізією й заявками на унікальність |
| `edits/{card}/{editor}` | Одна `update`-пропозиція на автора й ціль. Збережено зміни, відомі початкові значення, зв’язки пар замін і прив’язку до активної чернетки, коли вона однозначна |
| `profileMutationHistory` і `editsHistory` | Події з ключем та вихідним вмістом. Зв’язок вказує на підтверджений слот пропозиції. Він не приписує авторові створення дії адміна і не вигадує ревізію за старим журналом |
| `profileMutationOwners`, `profileIdentityClaims`, `editsByEditor`, `editsContributors` | Вихідні вузли залишаються на своїх адресах. Підготовлений набір містить їхні зв’язки для звірки |
| `searchId`, `searchKey` і канонічні вузли | Точні вихідні значення, включно зі спільними й застарілими посиланнями. Звіт рахує застарілі посилання за чинним читачем `searchId` |

Ключ запису у підготовленому наборі обчислюється з повної старої адреси.
Логічний ID пропозиції лишається в `proposalJson`. Події з однаковим старим
ключем у різних гілках отримують незалежні адреси. JSON-рядки для даних
пропозицій і журналу зберігають `null`, порожні контейнери й відсутні поля
під час запису у RTDB. Журнал без поточного запису залишається доступним
як історія. Уже прийняті, архівні й відхилені профілі мають ознаку
`historical`. Частково розглянуте доповнення переносить залишок із головного
запису, а наявні завершені дії залишає в журналі.

`hold` означає, що перед використанням треба звірити окремий запис. Це
стосується незавершеної публікації або розгляду, суперечливих ID, даних без
підтвердженої цілі та поточного видалення акаунта. `authDeletedAt` відрізняє
підтверджене видалення від відсутності цілі у знімку. Історичний
`profileMutations` з `operation: update` має повний знімок анкети без
підтвердженої різниці. Цей запис зберігається сирим у `unmapped`, щоб не
перетворювати невідомий набір правок на пропозицію. Причини наведено в
`issues`. Події, які старий процес уже видалив, з поточного знімка відновити
неможливо.

## Переключення

Будь-яке застосування у production потребує окремого дозволу. Для репетиції
завантажте у локальний RTDB актуальні правила та синтетичний знімок.
`profileProposalControl/activeWriter` керує дозволеним писачем. Відсутній
стан і `legacy` дозволяють попередні шляхи. `frozen` закриває записи обох
гілок. `unified` відкриває лише `multiData/profileProposals/live` зі
звичайними перевірками ролей. Клієнти можуть читати тільки значення режиму.
Збірка `REACT_APP_PROFILE_PROPOSAL_STORAGE=unified` використовує єдиний
набір шляхів упродовж сесії, включно з офлайн-відновленням.

1. Після погодження релізу викотити правила RTDB, Cloud Functions і клієнт
   у режимі `legacy`. Пуш у `main` запускає всі три процеси, тож дочекатися
   успішного завершення кожного й перевірити старий сценарій. GitHub Pages
   читає `REACT_APP_PROFILE_PROPOSAL_STORAGE` із кроку збірки в
   `.github/workflows/deploy.yml`. `legacy` збирає старий режим,
   `unified` — новий. Коміт, що змінює режим, запускає збірку Pages.
2. Призупинити адмінський розгляд і остаточне очищення акаунтів. У режимі
   `legacy` дочекатися завершення наявних операцій, включно зі старими
   вкладками, які могли писати канонічні дані без міток розгляду. Підготовка
   вимагає відсутності `cleanupLease`, незавершеної публікації й
   `reviewClaim`. Потім встановити `frozen` привілейованим записом поля
   `activeWriter`, зберігаючи решту контрольного вузла. У цьому режимі
   записи пропозицій, зокрема завершення розгляду, заблоковано. Якщо свіжа
   перевірка знаходить незавершену операцію, повернути `legacy` під тією ж
   паузою, завершити операцію і повторити заморожування.
3. Зняти свіжий експорт, підготувати й перевірити весь набір. Звірити джерело
   повторним читанням під тим самим блокуванням. Перевірити кожен `hold` та
   `unmapped`, авторство, історію, видимість, пошук і збереження канонічних
   значень. Інший хеш означає потребу повторити підготовку зі свіжого джерела.
   Звірка охоплює цілі корені канонічних вузлів та індексів. Навіть вхід,
   збереження через `/my-profile` або фоновий запис можуть змінити хеш.
4. Підготувати патч `live` із замороженого знімка. Записати підготовлений
   архів із `staged.json` і перевірений `live` лише у
   `multiData/profileProposals`. Повторити звірку зі свіжим живим знімком,
   поки режим лишається `frozen`. `--allow-held` підтверджує, що перелічені
   записи лишаться доступними в архіві для звірки. Активні мітки цей прапорець
   не обходить. За ще заморожених записів окремим комітом змінити
   `REACT_APP_PROFILE_PROPOSAL_STORAGE` на `unified` у кроці збірки
   `.github/workflows/deploy.yml` і дочекатися публікації збірки з `main`.
5. Безпосередньо перед активацією ще раз звірити свіжий експорт і хеш `live`.
   Якщо джерело змінилося під час збірки, залишити `frozen`, звірити й
   замінити підготовлений набір зі свіжого знімка. Після успішної звірки
   одним серверним записом задати `activeWriter: unified` і `activatedAt`
   з поточним серверним часом у мілісекундах. Час відсіює відкладені події
   імпорту з журналу активності. Перевірити новий режим збіркою з прапорцем
   `unified`, а старий клієнт перевірити на відмову записів. Зберегти старі
   вузли й резервну копію для звірки.
6. Якщо новий писач ще не прийняв записів, відкат прибирає лише перевірену
   копію `live`, повертає `legacy` і відновлює збірку Pages у режимі
   `legacy`. Після першого нового запису спочатку
   зупинити записи, зберегти нові рішення й звірити їх з канонічними вузлами.
   Файловий відкат відтворює стан підготовки, тож для цього випадку потрібен
   окремо прорепетируваний перенос нових записів.

```bash
npm run prepare:profile-proposal-cutover -- --snapshot "$bundle/staged.json"
npm run prepare:profile-proposal-cutover -- --snapshot "$bundle/staged.json" --output "$bundle/live.patch.json"
```

Команда готує лише локальний патч. Знімок `staged.json` для цього кроку має
походити з RTDB, в якому серверний режим уже `frozen`.

## Запуск із порожнім сховищем

Production запущено з порожнім сховищем у [релізі `4cda1b0d`](https://github.com/KnowMe-app/main/actions/runs/45719430010).
CI перевірив застарілі пошукові посилання, порожній `live` і відсутність
активних операцій. Сервер перейшов у `frozen` умовним записом, а в
`unified` — після перевірки, що публічний сайт віддає JavaScript цієї
збірки. Одноразові кроки активації прибрано зі звичайного деплою.
Старі пропозиції та індекси збережено.
Посилання на чернетки без канонічних анкет не утворюють результатів у
новому клієнті, бо він відкриває лише доступну канонічну анкету або
чернетку з активного сховища.

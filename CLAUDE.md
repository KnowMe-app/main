# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

KnowMe — застосунок для ведення анкет донорок і матчингу: CRA + React 18, Redux Toolkit,
styled-components, Firebase (Auth, RTDB, Storage, Firestore), деплой на GitHub Pages.
Мова коду й коментарів у репозиторії — англійська для ідентифікаторів, українська для
пояснень «чому». Тримайтесь цього ж.

## Команди

```bash
npm install
npm start                 # dev-сервер, http://localhost:3000
npm run build             # прод-збірка в build/
npm run lint:js           # eslint по src/**/*.{js,jsx}; має завершуватись кодом 0
npm test                  # watch-режим
CI=true npx react-scripts test --watchAll=false                          # весь набір один раз
CI=true npx react-scripts test --testPathPattern "cardIndex" --watchAll=false   # одна сюїта
npm run test:rules        # сценарії доступу в емуляторі RTDB (потрібна Java)
```

У веб-сесії залежності ставить `SessionStart`-хук (`.claude/hooks/session-start.sh`) —
контейнер клонує репозиторій без `node_modules`, і без цього кроку `npm run lint:js`
бере глобальний eslint з образу (v10), який не читає `eslintConfig` з `package.json`,
і падає на порожньому місці. Локально хук — no-op (перевіряє `CLAUDE_CODE_REMOTE`).

`npm run test:rules` піднімає емулятор через `firebase-tools` і прогоняє
`scripts/rulesEmulatorTests.mjs` — понад сто перевірок доступу. **Це єдиний спосіб
дізнатись, що `database.rules.json` узагалі можна задеплоїти:** мова правил має власний
діалект регулярок (`\s` і `\S` у ньому немає), і файл із непідтримуваною конструкцією база
відхиляє **цілком**, лишаючи в проді попередній набір правил. Прогоняйте його після кожної
правки правил; у `npm test` цю пастку ловить лише `databaseRulesRegexDialect.test.js`.

Кілька сюїт падають незалежно від змін (мок `localStorage` у них повертає `null`):
`cardsStorage`, `load2Storage`, `dplStorage`, `favoritesStorage`, `getFilteredCardsByList`,
`AddNewProfile.makeIndexGate`, `Matching.sharedReactions`. Перед тим
як щось «лагодити», звірте з чистим `main` — інакше згаєте час на чужу поломку.

Але й не списуйте червоне на цей список не глянувши: `profileLayoutConfig` лежав у ньому
не через мок, а тому що описував поведінку, якої в коді ще не було («стерте поле не
показувати»). Полагодив його код, а не тест.

## Візуальний дебаг у браузері

Частина того, що ламається в матчингу, тестами не ловиться взагалі: правило, яке
мовчки не доїжджає до сторінки; картка, що зникає з-під пальця; смужка, яку код
малює під рамкою й тому не видно. Це перевіряється очима — і перевіряється
локально, живим застосунком, а не задеплоєним: у проді стоїть старий код.

**У веб-сесії для цього все є.** В оточенні контейнера лежать і конфіг Firebase
(`REACT_APP_API_KEY`, `REACT_APP_AUTH_DOMAIN`, `REACT_APP_DATABASE_URL`,
`REACT_APP_PROJECT_ID`, `REACT_APP_STORAGE_BUCKET`,
`REACT_APP_MESSAGING_SENDER_ID`, `REACT_APP_APP_ID`), і доступ до тестового
акаунта (`MIGRATION_EMAIL`, `MIGRATION_PASSWORD`). Файлу `.env` при цьому немає
й не треба: CRA читає ці змінні просто з оточення, тож `npm start` піднімає
застосунок, підключений до справжньої бази `webringitapp`.

**Значень цих змінних не друкуйте** — ані в лог, ані в звіт. `env | grep`
пісочниця відхиляє сама (`Credential Materialization`), і це правильно: у
скрипті вони беруться з `process.env` і нікуди більше не потрапляють.

```bash
BROWSER=none PORT=3000 npm start &     # http://localhost:3000/main/ (basename="/main")
npm install --no-save playwright-core  # Chromium уже в образі, качати нічого
```

Три речі, на яких цей шлях ламався, і кожна коштувала окремого розбору:

- **Форма входу живе на `/login`, а не на `/`.** На корені стоїть
  `PrivacyPolicy` (або `AddNewProfile` — залежно від прав), і чекати там на
  `input[name="email"]` можна вічно.
- **Chromium треба явно пускати через агентський проксі — і вкоротити йому
  ClientHello.** Сам він `HTTPS_PROXY` не підхоплює, а з повним ClientHello
  релей рве тунель: `identitytoolkit.googleapis.com` віддає
  `ERR_CONNECTION_RESET`, Firebase каже `auth/network-request-failed`, і
  зовні це виглядає як невірний пароль (хоч той самий POST з `curl` дає 200).
  Робочий набір: `proxy: { server: process.env.HTTPS_PROXY, bypass:
  'localhost,127.0.0.1,::1' }` плюс аргументи `--no-sandbox --disable-http2
  --disable-quic --ignore-certificate-errors --ssl-version-max=tls1.2
  --disable-features=EncryptedClientHello,PostQuantumKyber,TLS13EarlyData`.
  Байпас для `localhost` обов'язковий — інакше дев-сервер відповідає 405.
- **Успіх логіну доводить екран, а не таймер.** `waitForTimeout(15000)` не
  гарантує нічого й тихо пускає сценарій далі з порожньою сесією. Ознака
  успіху — що поле пароля **зникло** (`state: 'detached'`); якщо форма лишилась,
  на ній стоїть помилка, і її текст треба прочитати й показати, а не проковтнути.

Селектори форми: `input[name="email"]`, `input[name="password"]`,
`#login-terms`, кнопка входу — остання кнопка з текстом «Увійти»
(`page.locator('button', { hasText: /^Увійти$/ }).last()`: вкладка над формою
зветься так само). Вибору ролі на вході **немає**: радіокнопки
`input[name="userRole"]` стоять лише на вкладці «Створити акаунт», — тестовому
акаунту їх не треба. Виконуваний Chromium — `/opt/pw-browsers/chromium-*/chrome-linux/chrome`
(номер збірки змінюється, беріть за маскою). `playwright-core` — CommonJS, тож в
ESM він імпортується дефолтним імпортом, а не `import { chromium }`.

Далі, вже на `/matching`, є ще дві пастки саме цього екрана:

- **`role="dialog"` на сторінці два** — панель фільтрів (`aria-label="Фільтри
  matching"`) і відкрита картка (`aria-label="Профіль"`). Селектор без
  `aria-label` ловить не ту, і кнопка картки «не знаходиться» там, де вона є.
- **Рядок стрічки не відкривається кліком у будь-яке місце**: усередині нього
  діти, що глушать подію (нотатка, ряд рішень, контакти). Клікайте по фото або
  по імені. Самі рядки й плитки несуть `data-card-id` — за ним зручно і шукати
  конкретну картку, і звіряти, чи вона лишилась у деці після реакції.

## Деплой

Пуш у `main` запускає `.github/workflows/deploy.yml`: install → lint → build → gh-pages.
`.env` збирається з GitHub Secrets, локально його немає.

**Правила бази CI не викочує.** `database.rules.json` деплоїться руками:
`npx firebase deploy --only database` (проєкт `webringitapp`). Зміна правил у репозиторії
сама по собі нічого в проді не змінює — це вже коштувало тижня, коли межа приватності
жила в коді й не діяла в базі.

## Архітектура

### Анкета розкладена по вузлах RTDB

`/matchingCards`, `/profileDetails`, `/profileContacts`, `/profileWorkflow`,
`/profileTechnical`; `/users` лишається **legacy-дзеркалом** — веб туди пише, але з нього
**не читає взагалі**: жодного `get` на `users/...` у коді немає, і додавати новий не
можна. Що читалось звідти раніше й куди переїхало: `publish` → `feedDate` у картці,
`accessLevel` → `profileTechnical`, `cycleStatus`/`lastAction`/`lastCycle` →
`profileWorkflow`, `lastLogin`/`createdAt` → `profileTechnical`, контакти → `searchId` і
`profileContacts`. Дзеркалиться лише анкета акаунта (довгий id — Firebase-Auth UID), і
питання «чи є legacy-тіло» вирішує формат id, а не читання
(`hasLegacyUsersBody`, `getCardLegacyCollection`). Виняток один і він явний:
кнопка «завантажити users.json» в адмінці — вона й існує, щоб вивантажити legacy
для міграції. Дзеркало не *створює* нового тіла: у `/users`
живуть анкети акаунтів (довгий id — Firebase-Auth UID) і ті картки, тіло яких
потрапило туди раніше. Картка, яку завела адміністраторка, тіла в `/users` не
отримує — ані при створенні (`makeNewUser`), ані при публікації чернетки
(`acceptCreateProfileMutation`). Розкладка описана декларативно в
`src/utils/profileNodeSchema.js` — це джерело правди і для міграції, і для runtime, і для
тестів правил. Деталі: `docs/rtdb-profile-nodes.md`.

`matchingCards/{id}` — проєкція під рядок стрічки (десяток скалярів + похідні
`surnameShort`, `rh`, `bloodGroup`, `avatar`). Контрактом володіє
`src/utils/matchingCardIndex.js`: `buildMatchingCardProjection` збирає, `expandMatchingCard`
розгортає назад у форму, яку читають рендер і фільтри.

`feedDate` — і допуск до стрічки, і порядок у ній. Станів три: **дата**
(`YYYY-MM-DD`) — картка в стрічці; **`false`** — анкету сховали навмисно
(«Приховати анкету» на `MyProfile`); **ключа немає** — анкету ще не публікували.
Стрічка бере лише перший стан (`startAt('')` пропускає самі рядки), а пошук — перший
і третій: у `searchId` лежать усі анкети, і мовчати про знайдене лише тому, що воно не
опубліковане, означає не відповісти на запит. Порядок видачі пошуку —
`src/utils/matchingSearchResultOrder.js`: спершу з датою, потім решта, сховані геть.

### Межа приватності: поза стрічкою видно саму картку

Це головна межа проєкту, і вона описана двічі — в базі й у коді:

- `database.rules.json` — `profileDetails/$uid` і `profileContacts/$uid` відкриті
  будь-якому авторизованому читачеві **лише поки в картці є `feedDate` у форматі
  дати** (`false` і відсутній ключ права не дають);
- `src/utils/profileVisibilityScope.js` — та сама умова в коді, який складає анкету.

Межа стоїть **до запиту, а не після відповіді**: `readProfileFromNodes` читає спершу
картку й рівень доступу, і лише довівши право, питає `profileDetails`/`profileContacts`.
Інакше контакти прихованої анкети приїжджали б у браузер, а не пускали б їх на екран
самі лише правила — ті, що викочуються руками.

Сама ж картка (`matchingCards/$uid`) відкрита кожному авторизованому незалежно від
`feedDate` — вона і є той мінімум, який видно поза стрічкою, і саме її показує пошук.

**«Авторизований» — це справді мінімум, і нижче він не опускається.** Незалогінений
читач не бачить нічого: `matchingCards` не відкривається анонімно й не буде. Причина
не в зручності, а в тому, що правила бази не вміють питати, звідки прийшов запит:
відкритий анонімно вузол — це `curl` по REST, який вивантажує весь каталог донорок
(імʼя, знімок, рік народження, місто, група крові) одним запитом, без обмежень
частоти й без сліду. Анонімний вхід Firebase (`signInAnonymously`) цього не лікує,
а робить гіршим: для правил така сесія нічим не відрізняється від агенції, тож разом
із карткою відкрились би `profileDetails` і `profileContacts` кожної опублікованої
анкети.

Тому межа входу стоїть на маршруті: `RequireAuth` у `App.jsx` не монтує захищений
екран, доки Firebase не скаже, хто читач, а незалогіненого веде на `/login`, несучи
з собою адресу, з якої він прийшов (`utils/authRedirect.js` — посилання зазвичай ведуть
усередину застосунку, і після входу людина мусить опинитись там, куди їй надіслали).
Публічних екранів три, і жоден з них не читає бази: `/login`, `/policy`, `/submit`.
Новий маршрут без гарда ловить `App.routeGuards.test.js`.

**Стан входу — це відповідь Firebase, а не позначка в `localStorage`.** «Ще не знаємо»
окремо від «не увійшов» (`authStatus`: `pending` / `in` / `out`): поки межа плутала
ці два стани, читач із живою сесією встигав побачити форму входу. З того ж боку —
позначка `isLoggedIn` тепер знімається, коли Firebase каже «користувача немає»:
протухла сесія з живою позначкою ганяла людину між формою входу й захищеним екраном
по колу.

**Стрічка без читача не питає базу взагалі.** Це не дубль межі, а другий її бік:
сесія протухає й посеред перегляду, вже після того, як екран змонтувався. `loadInitial`
і `loadMore` при порожньому `getOwnerId()` зупиняються й закривають `hasMore`. Поки
цього не було, незалогінена вкладка на `/matching` тримала відкритий сокет до бази й
слала по два-три запити `matchingCards` **на секунду** без кінця: кожен відлітав з
`Permission denied`, відмова летіла повз `.then` у `runAutoLoadMore`, лічильник
порожніх спроб не рухався — і стеля, яка стереже самохідний цикл, не спрацьовувала
ніколи. Тепер відмову ловить `.catch` і рахує за витрачену спробу: одна помилка бази
більше не перетворює довантаження на нескінченний цикл **і для залогінених теж**.
На екрані при цьому було «Owner not found» під вічним скелетоном — англійський рядок
у коді, що ні про що не казав і не давав звідси виходу; тепер там фраза мовою
інтерфейсу й кнопка на вхід.

Межа видна і в самій розкладці: рядок стрічки не малює кнопки контактів там, де за
нею нічого не стоїть (`canOfferProfileContacts` у `profileVisibilityScope.js`).
Значок обіцяв контакти й коштував круга до бази заради напису «Контактів немає або
вони закриті» — а правила додаткового доступу тут нічого не змінюють: вони доливають
картки в деку, `profileContacts` же відкриває лише `feedDate`. Винятків два, і
обидва про те, що читач набрав сам: власна чернетка
(`__profileMutationOperation === 'create'`) і картка, яка **вже несе контакт у
руках** (`cardAlreadyCarriesContacts`). Друге — це власне доповнення: у кеш
контакти не кладуть узагалі, а проєкція стрічки їх не несе, тож узятись їм
більше нема звідки. Доповнюють здебільшого картку, знайдену за контактом, тобто
неопубліковану, — і трубки в її рядку не було: право питали в бази, якій цього
номера ніхто й не збирався показувати.

**Про читача правила не питають нічого, крім того, що він авторизований.** Умова «роль,
відмінна від `ed`» тут була — і саме вона показувала донорці картку агенції без прізвища
й контактів: код цієї умови не повторював, а `readProfileNodePart` ковтає відмову навмисно
(контакти можуть бути закриті, і анкета мусить відкритись без них), тож назовні відмова
виглядала як порожня анкета. Умову знято; якщо порожня анкета зʼявиться знову — найпершим
підозрюваним лишається нерозгорнутий `database.rules.json`, і `readProfileFromNodes` пише
про такий випадок у консоль.

Службовий доступ (`accessLevel` містить `matching`), власниця анкети й адміни
(`ADMIN_UIDS` у `src/utils/accessLevel.js`) від межі не залежать. Рівень доступу читається,
а не вгадується: `resolveViewerAccessLevel` у `config.js` — ключ у `localStorage` зʼявляється
лише після мережевого круга, і відсутність ключа означає «прав немає», а не «можна все».

**Єдина воронка складання анкети — `readProfileFromNodes` у `src/components/config.js`.**
Сюди сходяться стрічка, пошук, реакції та гідратація за фільтрами; тут стоїть межа. Новий
шлях читання анкети веде сюди, а не в окремі `get`.

### Кеш карток

`src/utils/cardIndex.js` + `cardsStorage.js` тримають анкети в `localStorage`. Кеш
привʼязаний до `ownerId` і версіонований (`CARDS_CACHE_VERSION`) — підняття версії скидає
все збережене раніше. Контакти в кеш не потрапляють тому, чиє право на них тримається на
`feedDate`: право протухає в базі, а браузер про це не дізнається. Єдине місце цього
правила — `sanitizeMatchingCardForCache`; воно прикриває всі шляхи, що беруть картку з кеша.

**Сховища карток і списки id — окремі шари, і складає їх одне місце.** `cards`
тримає повні анкети (їх читає й екран редагування), `matchingSummaryCards` —
проєкції стрічки, `queries` — самі лише списки id зі своїм станом (`cachedAt`,
курсор, `hasMore`, умова). Картки для будь-якого списку складає
`composeCachedCards`: повна анкета, якщо свіжа й не старша за проєкцію, інакше
проєкція, а чого немає ніде — те дочитується точково (`hydrateMatchingFeedCards`),
а не список заново. Для редагування проєкція не годиться — там
`allowProjections: false`. **Список не урізається через те, що в одному зі
сховищ бракує картки**: `getQueryEntry` колись лишав тільки id з анкетою в
`cards` і записував урізане назад — і коли проєкції з `cards` прибрали
(`shouldCacheMatchingCard`), тихо померли всі списки з проєкцій: стрічка,
обране, приховані. Оверлеї й чернетки — шари, що накладаються при показі, у
кеш карток вони не вшиваються.

**Стрічка має свій список на кожну умову** — фільтри плюс роль читача,
`buildFeedListKey` (ключ — короткий хеш підпису, `feed:…`, не більше
`FEED_LIST_MAX_KEYS`). Поруч зі списком лежить стан пагінації
(`setQueryPagination`, рішення — `resolveFeedCacheResume`): дочитану стрічку
бекенд не питає зовсім, незакінчену дочитує від курсора. Повернення до
попередніх фільтрів теж береться з кеша. Зсув індексного провайдера курсором
джерела не є, і ці шляхи стан знімають.

**Старт сторінки не читає того самого двічі.** Кожен повтор тут був окремим
кругом до бази на кожне перезавантаження (64 читання → 24 на тестовому
акаунті), і тримають це кілька речей: `fetchUserById` ділить читання, яке вже
триває (`fetchUserByIdInFlight`); вхід передає прочитану анкету й ключі наборів
у `ensureFreshAdditionalMatchingProfile` (`prefetchedProfile`), а не дає
перечитати; підписки на реакції додаються й знімаються по власнику, а не всі
заново на кожну зміну переліку (`reactionSubscriptionsRef`), і `loadInitial`
бере їхній знімок (`readLiveReactionSnapshot`) замість `get` тих самих вузлів;
надані правилами картки памʼятає вкладка (`fetchLimitedProfileByIdMemo`); дата
входу пишеться раз на день із пристрою (`LAST_LOGIN_WRITTEN_KEY_PREFIX`), а не
на кожне відкриття, — кожен такий запис перебудовував власну картку з пʼяти
вузлів; класифікація реакцій бере `feedDate` з кешованої проєкції.
**Позначки власника (`getInTouch`, `writer`) анкета бере точково**
(`readOwnerValueForProfile`): `readProfileFromNodes` тягнув мапу власника
цілком — в адміна 160 КБ на кожному вході, заради поля, якого на екрані входу
немає. Мапа цілком береться лише там, де вона вже є (картотека
`AddNewProfile` завантажує `writer`, список «кому дзвонити» — `getInTouch`),
або коли однорядкова проба каже, що в `getInTouch` лишилась стара,
перевернута форма запису. **Список фото `Photos` читає один раз на анкету**
(`remotePhotosRef`): ефект залежить від `setState`, який «Мій профіль» передає
новою функцією на кожен рендер, і лістинг Storage з адресами кожного файлу
повторювався на вході по шість разів.
Перевіряти це — не тестами, а кадрами WebSocket у браузері: кожне читання
RTDB — це кадр `{"a":"g"|"q","b":{"p":…}}`, і лічильник по шляхах одразу
показує, що читається двічі.

### Пошук

Два індекси: `searchId` — точковий резолв «контакт → id» (перелічити вузол може лише
адмін, `docs/searchId-index.md`), `searchKey` — бакети для фільтрів
(`docs/searchKey-index.md`). Читач без повного доступу отримує урізану проєкцію
(`fetchLimitedProfileById`) і не сканує індекс.

**Ключ `searchId` — саме значення, а поле лежить у ньому**: `searchId/{значення}/{поле}`
= `id | [id, ...]`. Поле стояло в ключі (`{поле}_{значення}`) — і за це платив кожен
пошук: читач не знає, у якому полі лежить набране, тож питав усі, а `SearchBar` робив на
кожне поле окремий пошук зі своїм кешем і гідратацією. Тепер запит читає один ключ, а
поле приходить у тому ж записі, тож звуження до поля (`searchIdPrefixes`), підпис видачі
(`__searchIdFields`) і перевірка зайнятості в чернетках коштують нуль запитів. Форму
знає одне місце — `src/utils/searchKeyUtils.js` (`buildSearchIdValueKey`,
`buildSearchIdEntryPath`, `readSearchIdEntryIds`); нормалізацію набраного вибирає поле,
яке розпізнав `SearchBar` (`searchIdDetectedField`), а не перебір полів. Старий експорт
переводиться офлайн: `node scripts/convertSearchIdIndex.js`.

**Чернетки теж лежать у `searchId` — і тільки в ньому.** Чернетка
(`multiData/profileMutations`, `operation: 'create'`) картки стрічки не має, тож зведення
з пʼятьох вузлів її не бачить, а перебудова, залита заміною вузла, зносила б рівно ті
записи, якими чернетка боронить себе від дубля. Обидві перебудови читають її окремо
(`loadProfileDraftsForIndexing`, файл `profileMutations-*.json` у локальній збірці) і
кладуть **лише** в `searchId`: у `searchKey` і `matchingCards` живе стрічка.

Кладе її туди й **сама чернетка, на кожному збереженні** —
`indexDraftSearchIdEntries` у `saveCreateProfileMutation`. Доти запис стояв самим
лише в `acceptCreateProfileMutation`, тобто аж на публікації: заведений номер до
індексу не доїжджав узагалі, на нього ставили саму лише заявку на унікальність
(`profileIdentityClaims`), а вона стереже дубль і пошуку не відповідає. **Правила
під цей запис треба викотити руками** (`npx firebase deploy --only database`):
право дає наявність власної чернетки під цим id, так само, як оверлей дає право
індексувати дописане. Відмова збереження не валить (автозбереження спрацьовує на
кожному blur, і загублена анкета коштує більше, ніж ненаписаний ключ), але
називає ключ — тостом адмінові й `console.warn` усім.

**Право авторки чернетки — завести запис, а не переписати його.** Правило так і
написане (`newData.isString() && !data.exists() && ...`), тож транзакція, яка
повертала те саме значення, що вже лежить у ключі, відлітала з
`PERMISSION_DENIED` — на кожному blur і по ключу на кожне індексоване значення.
Памʼять таба не рятувала: вона ставиться після круга, що скінчився без відмови,
а цей не вдавався ніколи. І коштувало це не лише круга до бази: відмову видно
людині, тож застосунок щодотику повідомляв, що набраний телефон **не потрапив**
в індекс, хоч той лежав там з першого ж збереження — тобто сам і описував
неіснуючий баг. Тепер `addCardIdToSearchIdEntry` повертає `undefined` (перериває
транзакцію), коли дописувати нема чого; дописати id в одиночний рядок чи в
масив — зміна, і правила її пропускають, тож ключ, у якому цієї картки ще
немає, пишеться як писався.

**Знайдену чужу чернетку читають точково, за мапою авторів.** Шлях до чернетки
починається з автора (`multiData/profileMutations/{автор}/{картка}`), а пошук
дає з `searchId` самий лише id картки — автора з нього не дістати. Тож
прочитати знайдену **чужу** чернетку можна було єдиним способом: узяти вузол
цілком, а це службове читання «хто що завів по всій базі», і має його адмін та
власник `canCreateProfiles`. Звичайний читач на той самий точний номер бачив
«Не знайшов» і заготовку «Створити нову» — а натиснувши її, діставав
`DUPLICATE_PROFILE`: номер тримає заявка на унікальність. Пошук казав «такої
немає» рівно там, де вона є, і пропонував завести дубль, який база не приймає.
Тепер автора називає `multiData/profileMutationOwners/{картка}`, і форма в
нього та сама, що й у заявок на унікальність: **ключ** відкритий кожному
авторизованому, **перелік** лишається службовим — інакше це був би список усіх
id чернеток. Пише пару сама чернетка, раз на таб на картку
(`indexDraftOwner`), а старим чернеткам її дописує окрема робота панелі
індексації на `AddNewProfile` — чекбокс «Автори чернеток»
(`backfillProfileDraftOwners`). Стояла вона спершу в `createSearchIds` — на
вигляд саме там, де й має бути, — і не запускалась **ніколи**: ту функцію не
викликає ніхто (імпорт у `AddNewProfile` закоментований), а живої перебудови
`searchId` на бекенді в панелі немає взагалі. Перш ніж вішати щось на
«перебудову індексу», звірте, чи ту перебудову хтось запускає;
`AddNewProfile.draftOwnersJob.test.js` стереже, що чекбокс є, що його бачить
гейт «оберіть хоча б один» і що кнопка справді кличе бекфіл. Читання чужої чернетки
коштує два точкові запити замість вузла на всю базу, а вузол цілком лишився
запасним шляхом для службового читача. **Правила під це треба викотити руками**
(`npx firebase deploy --only database`) — і доти все лишається як було: мапа не
пишеться (тост адмінові з назвою ключа) і не читається, тож чужу чернетку
знаходить самий лише службовий читач.

**Знайдена чернетка показується з самої чернетки.** Вузлів анкети в неї немає, а
`profileDetails`/`profileContacts` під неопублікованою карткою закриті правилами,
тож `readProfileFromNodes` віддає про такий id `null` — і пошук, який щойно знайшов
id за набраним номером, відповідав «Не знайшов», та ще й клав у кеш **негативне**
влучання, тобто мовчав і на наступний той самий запит. Видно чернетку було рівно
її авторові й рівно на `/matching`, де її доливає окремий шлях
(`personalDraftSearchMatches`); адмінка на той самий номер відповідала порожнечею.
Тепер після порожньої анкети `addSearchHit` питає саму чернетку
(`readProfileDraftForSearchHit`): спершу власну, точковим читанням, а потім — якщо
читач має право на вузол цілком — весь перелік, раз на таб. Відмова в правах теж
памʼятається: інакше звичайний читач платив би за неї на кожному влучанні.

**Питання «чи це значення вже в `searchId`» ставиться індексу, а не анкеті.** Обидва
писачі (`syncUserSearchIdIndex` і цикл усередині `updateProfileNodesInRTDB`) колись
дописували ключ лише тоді, коли значення було нове **для анкети** — і значення, яке
потрапило в анкету повз індексатор (імпорт, міграція, прийнятий овнерлей, відмова бази
на попередній спробі), не індексувалось уже ніколи: кожне наступне збереження бачило
«не змінилось». Виглядало це як анкета з прізвищем, якої пошук за прізвищем не знаходить.
Тепер індексуються всі подані значення, а ціну читань тримає `confirmedSearchIdEntries`
в `config.js` — памʼять таба про вже підтверджені пари «ключ → анкета».

**Влучання в `searchId` не перевіряють анкетою.** Ключ індексу — саме значення,
поле відсіює сам індекс (`fields` у `collectUserIdsBySearchIdKeys`), тож id з
такого ключа — це вже доведений збіг, і `doesCardMatchSearchParams` на ключі
`searchId` просто повертає `true`. Значення ж в анкеті може не лежати зовсім, і
то не поломка індексу: **доповнення читача** пишеться і в `searchId`
(`saveOverlayForUserCard`), а в картці його немає й не буде, та й **попередня
версія поля** лишається в індексі навмисно (ключ знімає лише явний намір). Поки
збіг звіряли з полем анкети, це коштувало рівно адмінові: на сторінці matching
картка показувалась (там вона проєкція, і перевірку пропущено), а `AddNewProfile`
на той самий запит відповідав «Не знайшов» — бо читає повну анкету.

**«Мій профіль» індексує кожне індексоване поле, а не сам лише телефон.** Умова в
`saveFieldValue` була саме про телефон (`isSearchIdIndexedField` тепер), і анкета з
прізвищем, поштою чи телеграмом, набраними тут, за ними не знаходилась: поза цією
гілкою `syncUserSearchIdIndex` з «Мого профілю» не викликається ніде, а
`updateDataInRealtimeDB` індексу не чіпає взагалі.

**Відмова індексації не валить збереження, але й не мовчить.** `updateSearchId` ковтає
помилку навмисно — `PERMISSION_DENIED` на одному ключі не має коштувати людині набраної
анкети, — проте адмінові показує тост із ключем і причиною
(`reportSearchIdIndexFailure`, стабільний id, щоб десяток кандидатів не склав вежу).
Донорці на реєстрації цей текст не означає нічого, тож там відмову й далі ловить
`console.warn` в `authProfilePersistence`. Позначка про підтверджений ключ ставиться
**після** вдалого запису, тож те, що не записалось, наступне збереження пробує знову.

**Знімає ключ лише явний намір адміна, і несуть його два різні канали.** Стерте
поле — `deletedKeys` (четвертим аргументом у `syncUserSearchIdIndex`; поки
`AddNewProfile` його не передавав, не знімалось нічого, а для анкети акаунта це
був єдиний шанс: `updateDataInRealtimeDB` індексу не чіпає). Прибрана версія
масиву — `pruneSearchIdValues`: `delCondition` тут не годиться, бо зносить поле
цілком, а решта версій чинні. Обидва йдуть **після** запису анкети — писачі
дописують у `searchId` усе, що є в payload. А позначка стирання (`['Оксана', '']`)
не знімає нічого навмисно: так «стирає» не-адмін, який пише овнерлей, а не анкету,
і порожній рядок не дає ні кандидата, ні ключа. Деталі: `docs/searchId-index.md`.

### Трафік стрічки

Один запит на сторінку карток замість повних анкет, кеш проєкцій окремо від кеша анкет,
фото — лише для того, що на екрані. Мотивація і цифри: `docs/matching-feed-traffic.md`.
Перш ніж додавати читання «на кожну картку», прочитайте цей документ.

**Стрічка гортається сторінками без паузи — для будь-якого читача**
(`MATCHING_FEED_PAGE_SIZE` у `utils/matchingFeedPaging.js`, 10 карток; наступну
сторінку сентинел просить за кілька екранів до кінця, `rootMargin: '2000px'`).
**Перша сторінка коштує рівно порцію**: запас джерела утричі — лише з другої
сторінки джерела (`getSourceLimit`), а вікно пейджера без курсора — рівно
`limit + 1`, з курсором — плюс `MATCHING_CARDS_CURSOR_DATE_SLACK`. Доти перша
сторінка тягнула 154 картки (~35 КБ) заради 24, а холодне відкриття стрічки —
~95 КБ (тепер ~29). І фото без аватара питаються **раз** на картку
(`photoHydrationRequestedRef`): ефект перезапускався, поки запит летів, і
картка коштувала три читання й три лістинги Storage. Тут стояла пауза для не-адміна: дві
картки на десять секунд із відліком і окремим жестом на кожну порцію. Вона
берегла ~11 КБ на сторінку й коштувала агенції близько двадцяти хвилин чекання
на двісті анкет — не повертайте її як «стелю на трафік».

**Курсор стрічки стоїть на останній взятій картці, а не в кінці сторінки
джерела.** Сторінку `matchingCards` питають із запасом (утричі більше за
потрібне), і курсор у кінці сторінки губив усе видиме, що на ній лишилось
понад потрібне: на порції з двох карток — до дев'яти зі сторінки в одинадцять.
Агенція бачила близько п'ятдесяти анкет із двохсот сімдесяти, а тоді джерело
«закінчувалось», і стан «дочитано» лягав у кеш на весь TTL — стрічка казала
«під ці фільтри більше нічого не підійшло» без жодного фільтра. Позиції карток
сторінки віддає сам пейджер (`cursorsByUserId` у `fetchMatchingCardsPage`), а
`collectFilteredMatchingSourceCards` бере курсор останньої взятої
(`getSourceCursor`). Кеш стрічки впізнає «свій» стан і за версією пагінації
(`MATCHING_FEED_PAGING_VERSION` у підписі `buildFeedCacheSignature`): коли
збережений курсор міг бути записаний хибно, версію треба підняти, інакше старий
стан переживе виправлення.

На широкому екрані стрічка — сітка (`hooks/useFeedColumns`: список до трьох
колонок, галерея до чотирьох; межі ширини — ті самі числа в стилях). Сітка йде
рядками, а не CSS-колонками: порядок задає дата публікації, і друга за
свіжістю картка стоїть поруч із першою.

**Стрічка адміна гортається за `profileTechnical/lastLogin`**
(`fetchAdminLastLoginCardsPage`). Реєстрація акаунта одразу записує `lastLogin`
тією самою датою, що й `registrationDate`, а наступні входи оновлюють його.
`profileTechnical` уже має `.indexOn: lastLogin`, тому сторінка читається одним
запитом `orderByChild('lastLogin')` + `endBefore(дата, id)` + `limitToLast`;
окремого вузла `adminRecent`, його backfill і подвійного запису більше немає.
Адмінські картки несуть `__adminLastLogin`, тому фільтр видимості пропускає і
сховані анкети. Анкети, створені редактором без реєстрації акаунта, `lastLogin`
не мають і в цю стрічку не входять — це свідомий наслідок сортування лише за
фактичними входами.

### Програми агенцій і клінік

Агенція чи клініка веде кілька програм одночасно (Україна й Грузія, різний вік,
різні доплати), і кожна — окремий запис зі своїми вимогами, **головною сумою**,
**доплатами** і тим, що покриває (`utils/donorPrograms.js`). Порядок програм
задає агенція (`order`), неактуальну вона ховає (`hidden`) — прихованої не
бачить ніхто, крім редактора.

**Виплат і доплат не два списки, а один: усе понад головну суму — доплата**
(досвід, вік, кількість клітин, повторна донація, щомісячні, перенос, КС,
двійня — відомі ключі в `PROGRAM_PAYMENT_FIELDS` плюс дописані агенцією;
`listProgramBonuses`). Так їх звуть самі агенції. Тут були три категорії
(гарантовані виплати графіка, можливі доплати, оплата окремої процедури) і
вибір «Як рахувати» на кожній виплаті (`counting`: додається / уже входить /
окремо), а картка показувала «Виплати», «За окрему процедуру», «Можливі
доплати» й плашку «Сценарій з відміченими доплатами» — три числа про одну
програму; це прибрано на прохання власниці продукту, не повертайте.
`counting` і `featured` більше не читаються й не пишуться. Нові дописані
доплати редактор кладе в `otherPayments` (лише там правила приймають і
`when`, і `condition`), а старі `bonuses` переносить туди на першій правці.

**Сума програми рахується просто й одним місцем — `programBreakdown`**:
основна виплата плюс **гарантовані** (`guaranteed`). Виплата понад основну
буває двох родів (`isGuaranteedPayment`): гарантована (типово щомісячні,
перенос, договір — `DEFAULT_GUARANTEED_PAYMENTS`; агенція перекладає будь-яку
позначкою `guaranteed` на виплаті) і **додаткова** (КС, двійня, досвід, усе
дописане). Заголовок картки — кого шукають («Шукаємо донора ооцитів»), а під ним
окремим рядком гарантована сума: «Винагорода від 1 500 $», поки є невідмічені
додаткові виплати, і просто «Винагорода 1 500 $», коли їх немає (через тире в
одному рядку сума читалась як ціна). У деталях основна й гарантовані стоять
рядками («Виплати»), додаткові — перемикачами, **типово знятими**
(«Додаткові виплати»), і відмічене читачкою додається до заголовка (`total`).
Поки в суму йшло все, заголовок обіцяв гроші за двійню кожній. **Правила під
`guaranteed` треба викотити руками**; доти `writeProgramsToDb` пише без нього
(`stripNewestProgramFields`), і виплата бере типовий рід. Підпису «Разом донорці за програму»
(`programPayLabel`) і власної назви програми (`name`) у картці й редакторі
більше немає; `name` лише переживає нормалізацію. `max` (з усіма доплатами;
історично `guaranteed`) — те саме число в діапазоні рядка, фільтрі й сортуванні
(`programGuaranteedUsd`). Щомісячна доплата — сума × місяці
(`payments.monthly.months`); не вказала агенція — береться 9, і сума стає «≈».
Ручного поля «Загальна сума» в редакторі немає; старий `payments.total`
показується лише в програми без головної суми. Інша валюта йде в суму за
курсом і робить її «≈» (крок 10, для гривні 100), без курсу — окремою
частиною. **Одяг — покриття лише програми СМ** (`listCoverageOptions`):
донорській редактор його не пропонує, а картка не показує.

**Програма в картці — окремий контейнер, а не рядок без меж** (`AgencyProgramsPanel`
у `programs/ProgramsView.jsx`). Картка організації йде своїм порядком: назва,
плашка ролі, місце → «Програми · N» з перемикачем валюти → контейнер на
програму → контакти → стислий ряд (відгук, памʼятка, реакції, олівець —
`organisationLayout` у `ProfileRow`, `compact` у `ProfileNotes`) → **«Більше
про агенцію» / «Більше про клініку» в самому низу**. Над програмами цей розділ
відсував їх на другий екран. Картка біологічних батьків так само кінчається
«Більше про біологічних батьків» (`parentsLayout`) замість «Детальніше»
посеред картки. Кожне розгортання підписане тим, що відкриває: «Деталі
програми» в контейнері програми, «Більше про …» під реакціями.
Опис організації в `matchingCards` не лежить, тож до читання анкети розділ —
сама кнопка; опис, що повторює місто чи назву («київ»), не показується
(`isMeaningfulOrganisationDescription`), а прочитана анкета без опису каже
«Агенція ще не додала опису» (`__fullProfileHydrated` у `withLazyPhotos`:
прапорець проєкції лишається й на зведеній картці).
Згорнутий контейнер: кого шукають (`PROGRAM_OFFER_LABELS` — «Шукаємо донора
ооцитів» / «Шукаємо сурогатну маму», а не роль «Донор ооцитів») і рядок
«Винагорода [від] …» (сума **у валюті читача**, оригінал дрібніше
під ним — `presentMoney`), місце з великої літери (`formatProgramPlace`),
**усі вимоги** чіпами зі збігом з анкетою читачки, до чотирьох ознак
(`resolveProgramHighlights` — вимог серед них немає) і коментар організатора
(`note`, три рядки). Рядок «Покриває: …» тут стояв і поступився вимогам —
покриття тепер лише в деталях. Курс і дата — один раз під програмами.
Ознаки, якими програма відрізняється від інших програм **того ж типу**,
підсвічені (`listProgramDifferences`). **Порожня програма — чернетка**
(`isProgramPresentable`): `listPrograms` її читачам не віддає, редактор
(`includeHidden`) тримає. **Організацію називає назва**: у анкеті агенції
`name` — назва, `surname` — контактна особа, `birth` — її дата, тож рядок без
`isOrganisationIdentity` у `ProfileRow` складав «Surrohelp M., 43».
Старий `title` програми не читається свідомо (прибраний 30.09, у старих
записах дублює місце).

**Програма з оголошення — спільна структура з гнучким змістом.** Виду суми
(`payKind`, `payMax` «до …») більше немає: вибір «Що означає головна сума?» з
поясненнями прибрано на прохання власниці продукту, основна виплата одна й
рахується як фінальна, а старі `payKind`/`payMax` нормалізація не читає. У
основної виплати й кожної іншої — `when` і `condition` (`includes` лише переживає
нормалізацію); переїзд
(`relocation`), як саме покривається витрата (`coverageDetails`: оплачує,
компенсує за чеками, видає кошти, входить у винагороду, межа, примітка);
своє агенції понад перелік покриття — подарунки, аванс (`customCoverage`,
рядки до 60 знаків, у картці з подарунком замість значка витрати);
вибрані агенцією ознаки (`highlights`, `['none']` — зняла все). Ознаки
генеруються з полів, тексту агенція не пише — інакше згорнута картка й вимоги
розійшлись би з першою правкою. **Рівнів вимог («бажано», «індивідуально», «без
обмежень») і пояснень до кожної (`requirementMeta`, `level` своєї вимоги) та
етапів з місцями (`stages`) більше немає** — прибрано на прохання власниці
продукту: нормалізація їх не читає, тож перший запис програми їх знімає, а
вимога в картці — саме значення і відмовляє за ним. Вибору ознак у редакторі
теж немає (розділ «Як виглядає в картці» прибрано) — картка бере типові або
вже збережені.
**Правила під ці поля треба викотити руками** (`npx firebase deploy --only
database`). Доти `writeProgramsToDb` повторює запис без них
(`stripExtendedProgramFields`), повна версія лишається в браузері власниці з
`pending` і не перебивається базовою (`isFresh`, `fetchPrograms`).

**Редактор програм — чотири розділи, що згортаються окремо** (`ProgramsEditor`):
основне (тип, «Місце програми» без підказки під ним, «Коментар організатора»;
«Старт одразу» прибрано як шум — видно лише вже поставлений, щоб його зняти) →
виплати («Основна виплата», під нею «Інші виплати» — кожна із сумою, позначкою
«Сумується автоматично до загальної винагороди» (`guaranteed`) і «+ Коли
платять»; підсумок «Сума програми» формулою «23 000 $ + 600 $ × 8 + 300 $» і
«З додатковими виплатами — до …») → вимоги до кандидатки (вік завжди, решта —
«+ ІМТ», «+ Резус»…, і «+ Своя вимога» — сам текст агенції,
`customRequirements`) → «Додатково» (покриття, «+ Своє: подарунки,
аванс…», переїзд). Текстові поля ростуть під текст (`AutoGrowTextarea`: Enter
нового рядка не додає, значення лишається одним рядком) — у `<input>` довгий
текст було видно шматком; назва доплати лишається `<input>` заради `list`
(підказки `programTerms`). Те саме поле — у правці рядка Flow. Розгорнуте
зʼявляється коротким `revealCss` (`styles/revealAnimation`) — одна анімація на
всі розкривні блоки анкети: програми (розділ, виплата, деталі, графік),
«Детальніше» рядка стрічки, блоки форми адміна (`ProfileForm`,
`NestedObjectField`, «Усі дані картки в базі»), історія правок у формі
доповнення, прев'ю «Мого профілю», меню уточнення пошуку. Ставиться лише на
те, що монтується саме розгортанням, — інакше блимала б уся форма на першому
показі.
**Виплата відкрита одна** (`openPayment`) і закривається кнопкою **«OK»**: вона
спершу знімає фокус (як blur — `MoneyInput` пише суму саме тоді), потім
згортає; влучити пальцем у порожнє місце не виходило, і відкривалась сусідня
виплата. Решта стоять рядком, яким їх покаже картка (назва, коли, сума — без
стрілки й без квадратика перед назвою: у темній темі він читався як відступ
абзацу; додаткова — сірою смугою ліворуч), а
щойно додана стає **в кінець** (`paymentOrder` — порядок додавання), сама
відкривається й бере фокус. Доти відома доплата ставала на своє місце в
переліку типу — часто над видимим, — і здавалось, що дотик не спрацював.
Кнопки-пропозиції не забирають фокус (`onMouseDown` + `preventDefault`):
`MoneyInput` пише суму на blur, і перерахунок зсував розкладку між дотиком і
відпусканням — додати доплату виходило з другого дотику. «Умов виплати»
(`condition`) більше не пропонує: агенції читали їх синонімом «Коли платять»;
старе значення видно й правиться, доки його не стерли. **Щомісячна СМ —
пропозиція, а не обовʼязок** (`SUGGESTED_PAYMENTS`): нова програма СМ
відкривається з нею, але прибирається вона, як будь-яка доплата.
**Правила під `customRequirements` і `customCoverage` треба викотити руками**;
доти `writeProgramsToDb` спершу повторює запис без них (`stripCustomCoverage`,
потім `stripCustomRequirements`).

**Приблизний графік програми СМ** (`ProgramTimeline` у деталях програми,
дати — `utils/programTimeline`): від першого дня місячних читачки (`lastCycle`
анкети: записане підставляється, порожнє вводиться тут, і введене пишеться
назад в анкету через `updateDataInRealtimeDB`) до пологів — перенос (робочий
19–22 день), ХГЧ (14-й день після), УЗД серцебиття (ще 14 днів), скринінги
12 і 18 тижня, договір з пологовим (36), пологи (40); галочка «Стимуляція з
дифереліном» переносить перенос у наступний цикл. Логіка робочих днів спільна з
графіком стимуляції (`utils/cycleDates`). Давні місячні відкладаються циклами
по 28 днів до найближчих. Донорським програмам графіка немає. Рядок — дві
колонки на весь список: ліворуч «27.11 пн (19 день)» (дата з днем тижня, у
переносу й дифереліну день циклу, далі тиждень вагітності), праворуч назва
події — без тире, усі назви з одного вертикального краю (`max-content` у
першій колонці; проміжок — відступом комірки, бо `column-gap` рвав риску між
рядками); де починається новий рік — рядок «2027» (`groupTimelineByYear`). Дата пишеться в анкету не лише таймером, а
й на blur, `pagehide` і розмонтуванні графіка: поки був сам таймер, обране за
мить до згортання деталей чи перезавантаження не доїжджало, і після
перезавантаження поле знову стояло порожнім.
Згорнутий розділ каже, що в ньому є («4 доплати · сума програми 32 600 $»), і
нічого не губить: значення живуть у програмі, а не в полях.
**Підпис над полем, поле на всю ширину**; сума з валютою, місяці, вік «від —
до» лишаються парою в рядку (`FieldRow`, `narrow` — стеля
ширини суми на широкому екрані). `flex-basis` полів стоїть лише в рядку: у
колонці він ставав висотою й розсував форму на екрани порожнечі. Порожньої
«Інша доплата» не стоїть двох — кнопка зʼявляється, коли попередню
заповнено. Приклади в полях — мовою програми (`TYPE_EXAMPLES`: «у день
пункції» донорці, «на 12 тижні» СМ) і короткі, щоб не обрізались на телефоні.
У анкеті агенції без
особистої ролі не пропонуються область і Twitter/LinkedIn/YouTube
(`ORGANISATION_SKIPPED_FIELDS` у `MyProfile`; записане значення лишається);
вимога поза межами бази (`REQUIREMENT_LIMITS`) каже про себе одразу, бо
`normalizeProgram` її мовчки відкидає, а рядок без суми чи назви — так само
(`listProgramIssues`). Поруч — той самий контейнер, що в стрічці
(`ProgramPreview`); на телефоні — вкладки «Редагування / Перегляд», кожна зі
своєю прокруткою. **«Готова до показу» означає й опубліковану анкету**
(`programStatus` з `profilePublished`): без публікації програму не бачить
ніхто. Стан запису стоїть у рядку вкладок і каже правду про частковий запис
(«Збережено частково…», коли правила бази ще не знають нових полів). Поки
програма відкрита, «Мій профіль» стискає липку панель прогресу до самих
вкладок, а її висоту віддає змінною `--km-sticky-offset` — під неї стають
липкий перегляд і прокрутка до розділу; `Card` там обрізає кути
`overflow: clip`, а не `hidden`, бо `hidden` ламає `sticky` усередині.
Відкладене записує й `pagehide`.

**Програми лежать окремо — `multiData/programs/{uid}` = `{ updatedAt, items }`,
а не в анкеті й не в картці.** Вони не приватні (читає кожен авторизований), але
в картці важили б більше за решту картки, а стрічка тягла б їх для кожного
рядка. Картка несе лише версію — `programsAt`, той самий `updatedAt`, записаний
тим самим `update` (`programsRemote.writeProgramsToDb`), і переносить її при
перебудові, як `hasPublicReview`. Читач бере програми **спершу з
`localStorage`** (`utils/programsStore`, ключ `programs:v1:{uid}`): збіглась
версія — запиту немає зовсім; ні — один точковий `get`, і лише тоді, коли
картка вже в списку (`useCardPrograms` у `CardRoleBlock`).
Власниця пише спершу в браузер з позначкою `pending`, тож відмова бази програм
не губить — «Мій профіль» дописує їх на наступному відкритті. Перша версія
клала програми в `profileDetails/{uid}/programs`; «Мій профіль» переносить
знайдене там і знімає з анкети лише після вдалого запису.
**Стислих програм (`programsBrief`) і послуг (`serviceTags`) у картці більше
немає**, лишився `seekingRole` батьків. Назви доплат, які вже вживають інші
агенції, — `multiData/programTerms/{payment|bonus}/{ключ}`: підказки в
редакторі, один запит на добу на браузер; дописати новий ключ може кожен,
переписати чужий — ні.

**Правила під `multiData/programs`, `multiData/programTerms` і
`matchingCards/…/programsAt` треба викотити руками** (`npx firebase deploy
--only database`). Доти програми не пишуться в базу (лишаються в браузері
власниці з тостом), а `syncMatchingCardIndex` пише картку без нових полів і
каже про це в консоль — інакше `$other: false` відкинув би картку **цілком**.
Те саме з `payments.monthly.months`: поки правила його не знають,
`writeProgramsToDb` повторює запис без місяців (`stripMonthlyMonths`).
`counting` і `featured` нормалізація більше не пише зовсім, тож перший відступ
(`stripNewestProgramFields`) для нових записів нічого не знімає; він лишився
для програм, збережених у браузері до цієї зміни.

**Ролей у людини буває дві** (донорка, яка ще й агентка): `updateProfileRole`
пише масив, основна роль **остання** — так її читає стрічка
(`resolveViewerCurrentRole`). У «Моєму профілі» при кількох ролях спершу
спільне (особисті дані, соцмережі — людина одна), далі анкета кожної ролі під
власним заголовком «Анкета · …», основна першою (`SHARED_SECTION_KEYS`,
`anketaRole`); у стрічці блок другої ролі підписаний роллю. Сховати одну з анкет —
`hiddenRoles` (рядок кодів через кому): картка сховану роль не несе, а сховати
всі не дає ні форма, ні проєкція — для цього є «Зняти з публікації». Ролі
«Мій профіль» бере з картки, доповнюючи схованими (`resolveMyProfileRoles`).

**Гроші: сума агенції — як її ввели, еквіваленти — за курсом НБУ на сьогодні**
(`utils/programCurrency.js`, `hooks/useProgramRates.js`; курс той самий, що й у
Flow, `fetchNbuUahExchangeRatesByDate`). Оригінал показується першим і без «≈»,
еквіваленти — з «≈» і датою курсу; власного курсу агенція задати не може, а без
курсу еквівалентів немає зовсім. «19.000 €» у чатах агенцій — це 19 000, і
`parseProgramAmount` так його й читає. У контейнері веб-сесії `bank.gov.ua`
закритий політикою мережі — для перевірки очима курс кладуть у денний кеш
`flow:nbu-uah-rates:{дата}`.

**«Підходить» рахує анкета читача** (`extractViewerProgramFacts` тими самими
функціями, якими її показує картка) і лише серед програм його типу: донорці —
донорські, СМ — свої. Невідоме в анкеті програму не ховає, а просить його
вказати. **Чіпів «Виплата» в рейці й сортування стрічки («релевантність»,
«виплата», «спершу нові») більше немає**: стрічка стоїть за датою публікації, а
збережена колись позначка «Виплати» деку не ріже (`keepViewerVisibleMatchingFilters`).
Межі сум (`PAYMENT_FILTER_BUCKETS`, `listPaymentBuckets`) лишились у
`donorPrograms` для картки програми.

Блок програм живе і в стрічці, і в «Моєму профілі», тож кольори в нього —
зі стрічки з запасними (`var(--matching-header-text, var(--km-text))`):
успадкований колір у стрічці бував білим на світлому, і суми зникали.

**Угорі «Мого профілю» — та сама картка стрічки** (`MyProfileCardPreview`,
`ProfileRow` з `preview`: без нотаток і ряду рішень), зібрана з набраного;
зʼявляється, коли набрано бодай два поля чи фото; картка — це набрана анкета плюс розгорнута проєкція (а не сама проєкція), тож у прев'ю є контакти й «Детальніше», як у читача, якому анкету відкрито; а кілька ролей стоять
перемикачем, а не повними картками одна під одною (дві картки з фото ставили
форму на два екрани нижче). Палітру стрічки поза нею оголошує
`MatchingThemeScope` з `Matching.styled.jsx`. «Послуги й досвід» з анкети
агенції прибрано (не заповнював ніхто), сайт — у «Соцмережах».

**Відкритої картки в стрічці немає.** Шар деталей (`SwipeableCard`,
`DetailLayer`) повторював рядок стрічки з більшим фото й прибраний разом із
гортанням деки стрілками: дотик до фото рядка відкриває саме фото на весь екран
(`PhotoViewer` з `closeOnHistoryBack` — темне тло, свайп, «назад» телефона
закриває), дотик деінде розгортає рядок. Згадки «відкритої картки» нижче —
історія; нотатки інших власників спільного доступу, які показувала лише вона,
тепер стоять у доріжці памʼятки рядка (`sharedNotes`). **Шапка форми
доповнення й чернетки — та сама картка стрічки** (`ProfileRow` з `preview`,
`DraftPreview`), а секції форми мають числа «Мого профілю»: картка без рамки з
радіусом `--km-radius`, заголовок смугою, поля з відступом 18 px і звичайною
вагою тексту. Своя шапка з іменем до 24 px розсипала імʼя на три рядки, а свої
відступи робили форму окремо скопійованим екраном.

**Видимість анкети вирішує один блок — «Публікація»** внизу «Мого профілю»
(`data-testid="publish-card"`), і статус у шапці веде саме до нього. При
одній ролі там статус і головна кнопка: «Опублікувати» — помаранчева,
«Зняти з публікації» — рамкою, не головна. **При кількох ролях кожна анкета
має свій рядок** — статус і кнопки «Опублікувати» / «Зняти» / «Очистити»
(`publishRole`, `unpublishRole`). Перемикачі «сховано / буде видно» тут
стояли й нічого не означали, поки анкету не опубліковано. Модель та сама:
роль опублікована = `publish` і роль не в `hiddenRoles`; перша опублікована
роль ховає решту, зняття останньої знімає з публікації картку. «Очистити»
питає ту саму модалку `DelConfirm`, що й пункт меню «⋮». **Одна анкета — опис і одна кнопка на всю ширину** («Опублікувати анкету» / «Приховати анкету»), без назви ролі й кошика (очистити — з меню «⋮»). **Кілька анкет — рядок на кожну**: ліворуч «Анкета донора» (`MY_PROFILE_ANKETA_LABELS`), праворуч спаяна пара, як серце з хрестиком (`RoleActionPair`): «Опублікувати» помаранчевим або «Приховати» рамкою плюс кошик «Очистити» в тій самій рамці; під назвою опублікованої — зелене «У стрічці». Слово «Приховати» тут — на прохання власниці продукту. Доти «сховати» стояло двічі різними
словами («Сховати» вгорі, «Приховати» внизу, і нижнє — лише після публікації),
стан звався трьома («Не опублікована», «Чернетка», «чернетка — профіль не
опубліковано»), а червоні «Очистити роль» стояли біля «Опублікувати».
**Незворотне — у меню «⋮»** (і «Очистити» в рядку ролі, через ту саму модалку): «Очистити дані: <роль>» (`clearRoleItems`),
«Очистити анкету», «Видалити анкету», і підтвердження в усіх одне — модалка
`DelConfirm` (`clearRoleTarget`), а не `window.confirm`. Порожнє поле, де сіра
підказка — значення («168», «Україна»), підписане «Наприклад: …»
(`asExamplePlaceholder`); формат («дд.мм.рррр», «username») і прохання
довші за три слова лишаються як є.

**Поле-обʼєкт у формі адміна** (`ProfileForm`) малює `NestedObjectField`:
згортані блоки, скаляр правиться на blur зі збереженням типу, кожен ключ і
блок знімається хрестиком. Доти обʼєкт падав у текстове поле як
«[object Object]», і перше ж збереження записало б цей рядок замість обʼєкта.

## Домовленості, які легко порушити необачно

- **Не вмикайте prettier масово, і не повертайте `.prettierrc.json`.** Конфіг тут
  був, але нічого не робив: prettier не оголошений ні в `package.json`, ні в
  локфайлі, і жоден скрипт та CI його не викликали. Небезпечний він був саме
  мовчки — редактор із format-on-save читає такий файл і переформатовує збережене
  за вас. А під той стиль не підходили 345 із 398 файлів: `prettier --write` по
  `src` дає ~46 000 рядків дифа й **ламає 19 тестових сюїт понад базові 7**
  (26 замість 7; 43 червоні тести замість 18) — через правило нижче, бо 69 тестів
  звіряють точний вихідний текст. Відступи й переноси описує `.editorconfig`;
  решту форматуйте вручну, у стилі сусіднього коду.
- Багато тестів читають **вихідний текст** модулів (`config.js`, `Matching.jsx`) і
  перевіряють у ньому конкретні рядки. Перейменування функції або зміна виклику ламає такий
  тест не тому, що поведінка інша, — виправляйте тест разом із кодом.
- Коментарі тут пояснюють **чому**, часто з історією регресії. Не замінюйте їх на переказ
  коду і не видаляйте, переписуючи поруч.
- `matchingCards` приймає лише перелічені поля (`$other: false` у правилах) — нове поле
  стрічки треба додати і в схему, і в правила, інакше запис відхилиться мовчки.
- **Вхід і реєстрація — дві вкладки** (`authMode` у `LoginScreen`). Ролі з
  поясненням під кожною (`ROLE_DESCRIPTIONS`) стоять лише на «Створити
  акаунт»; вкладка «Увійти» нікого не реєструє і, не впізнавши пошту, пропонує
  створити акаунт. Досі ролі зʼявлялись після невдалої спроби з тостом
  «Акаунта ще немає», а одруківка в пошті наявного акаунта вела в другу
  реєстрацію.
- **Довідник пропонує менше, ніж знає** (`legacy` у `formFields`,
  `utils/offeredOptions`). Значення лежать у базі англійськими словами, тож
  дублікати («Карі»/«Коричневі», «Темне»/«Брюнет») не видаляються: з них
  перекладаються записані анкети. Форма їх лише не пропонує — окрім значення,
  яке вже записане. «Свій варіант» біля Так/Ні — лише там, де є що уточнити
  (`YES_NO_DETAIL_FIELDS`).
- **Вхід роль не питає й не пише** (`buildAuthLoginPayload`). Форма входу
  вимагала обрати роль на кожному вході — лише «донорка» чи «агенція» — і клала
  її в Firestore `users/{uid}` та legacy `users/{uid}`, не чіпаючи картки: батьки
  після кожного входу ставали донорками чи агенціями, а «Мій профіль» (він читає
  анкету з Firestore) показував роль з останнього входу, хоч стрічка гортала за
  карткою. Тепер роль обирається при реєстрації — з усіх п'яти
  (`utils/profileRoleOptions.js`, той самий перелік, що й у «Хто ви»), — а
  «Мій профіль» показує роль з картки (`fetchProfileCardRole`), тобто ту саму,
  за якою гортає стрічка. Акаунти, в яких роль уже розійшлась, називає й
  вирівнює `node scripts/reportRoleDivergence.js` (суха прогонка; `--apply` —
  під адміном).
- Роль анкети змінюється з `MyProfile` і зберігається окремим шляхом
  (`updateProfileRole`, він пише й Firestore), а не автозбереженням форми: `deriveRole` **обʼєднує** `userRole`
  і `role`, тож запис самого лише нового значення лишає анкету ще й у старій ролі. Писати
  треба обидва ключі — і слідом пересунути бакет `searchKey/users/role`.
- Стрічка донорки показує самих контрагентів — `ag`/`ip`/`cl`/`pp`
  (`keepDonorCounterpartyCards`): вона відкриває список, щоб знайти агенцію, клініку чи
  батьків. **Ролі читача тут — набір, а не історія** (`listViewerHiddenCardRoles`):
  звужує деку лише читач, у якого всі ролі особисті (`ed`, `sm`), і ховає він
  анкети саме своїх ролей — донорка й СМ разом не бачать ні донорок, ні СМ;
  роль організації чи батьків знімає звуження цілком (донорка-агентка бачить
  усе). Від картки «донорка + агенція» донорці лишається агентська анкета
  (`listFeedRowAnketaRoles(user, hiddenRoles)`), агенції — обидві. Ролі
  читача стрічка бере з **обох** ключів анкети (`readViewerRolesFromProfile`):
  `userRole || role` губив другу роль, коли вона лежала в іншому ключі, і
  донорка-агентка гортала стрічку донорки. Ціна:
  акаунт, у якому `deriveRole` лишив стару роль поруч із новою, читається як
  обидві — такі вирівнює `scripts/reportRoleDivergence.js`. Умова саме така, а не «сховати колег»: картка **без ролі** (а таких у базі
  більшість) під «колегу» не підпадала й лишалась у стрічці — донорка бачила список
  невідомо кого. Правило діє лише в деці за замовчуванням: пошук такі анкети знаходить,
  бо там питання «де конкретна людина». Власна анкета й окремо надані картки з нього
  виключені.
- **Фільтри стрічки однакові для кожного читача, а «Тип профілю» донорки й СМ
  стартує з самих агенцій.** Донорці рейка малювала всі групи, а поповер
  пускав лише «Виплату» — дотик до «Типу профілю», «Сімейного стану» чи
  «Резусу» відкривав порожню панель. Умовчання особистої ролі
  (`resolvePersonalViewerRoleDefault`) ставить `FilterPanel` **раз на роль**
  (позначка `matchingRoleDefaultFor` у `localStorage`): порожні анкети батьків
  займали більшу частину стрічки, а далі батьків чи «Інших» читачка вмикає сама.
- **Чіпи «Типу профілю» донорці обіцяють більше, ніж її дека може дати.** У
  шухляді їх чотири («Донор ооцитів», «Агенція», «Біологічні батьки», «Інші»), а `keepDonorCounterpartyCards`
  лишає в деці самих контрагентів — тобто працюють рівно `AG` та `IP`. Знявши
  обидва, читачка задає умову, якої стрічка виконати не може, і коштувало це
  мовчки: код чесно обходив **усю** стрічку (277 карток, вісім кругів до бази)
  заради `filteredCardsCount: 0`, тоді закривав `hasMore` — а разом з ним гасне
  спостерігач за кінцем списку, тобто зникає й кнопка «Показати ще», —
  і лишав на екрані «Фільтри приховали всі завантажені профілі (N)», де N це
  картки наданого доступу, тобто напис про іншу причину. Виходу звідси не було
  взагалі: стелю порожніх спроб довантаження скидає прокрутка донизу, а крутити
  порожній список нема чого.
  Тепер цього стану досягти важко, і тримають його три речі. Шухляда й ряд
  чіпів беруть перелік опцій з одного місця — `listFeedRoleFilterKeysForViewer`
  через `resolveMatchingFilterGroups`, — тож донорці `ED` не показують ані там,
  ані там: чіп, який не може ані додати картку, ані прибрати, лише обіцяє
  вибір, якого немає. **Зміна ролі перебирає збережену групу за читача**
  (`alignRoleFilterGroupWithViewer` в ефекті `FilterPanel`): фільтри лежать у
  `localStorage` і переживають зміну ролі, тож агенція, яка гортала самих
  донорок, ставши доноркою діставала порожній екран — тепер знята позначка,
  якої більше не показують, вмикається назад, а якщо показаного не лишилось
  жодного, звуження знімається цілком. Переписується саме **стан**, а не показ:
  інакше позначка діяла б невидимо. І на випадок, коли читачка зняла `AG` та
  `IP` сама, лишається `donorFeedRoleFilterLeavesNothing` — причина словом і
  кнопка, яка вмикає обидва чіпи назад. Окремо: жоден `searchKey` тут не
  допоміг би — «крім X» з увімкненим `?` дає план `readMode: 'exclude'`, який
  кандидатів назвати не може, тож фільтрована дека й так іде звичайною
  пагінацією (`no include-mode filter group, deferring to source pagination`).
- **Загальний список — це стрічка, і нічого, крім стрічки.** Картка без дати у `feedDate`
  у деку за замовчуванням не потрапляє нізвідки, зокрема з правил додаткового доступу:
  вони читаються по індексу, який знає всі анкети, і колись доливали в деку
  неопубліковані. Неопублікована анкета — це відповідь точкового пошуку за контактом.
  Виняток один — власні чернетки (`personalCreateProfiles`).
- Хвіст деки належить пагінації: пачка наданих карток з входу стоїть
  **перед** нею (`__matchingAccessInitialBatch` у `mergeMatchingCandidateUsers`). Поки
  надані картки стояли після деки, кожна дописана сторінка лягала над ними, і «Додано N
  карток — вони в кінці списку» було неправдою. **Власні чернетки стоять у стрічці за
  датою створення** (`placeOwnDraftsInFeed`, `utils/matchingDraftPlacement.js`): головою
  деки вони висіли над усім, що зʼявилось після них. Чернетку, старшу за все
  завантажене, помічник не ставить у хвіст, доки стрічка має сторінки, — вона
  зʼявляється, коли стрічка дійде до її дати. Дата лежить у `__feedOrderDate`, а не в
  `lastLogin2`: за тим `isCardInMatchingFeed` вирішує, чи картка опублікована.
- **Масив у полі анкети — це історія, а не набір.** Телефон, імʼя, пошта в людини одні;
  масив тримає версії, і поточна серед них **остання** (`getCurrentValue` — єдине місце
  цього правила). Порожній рядок в останній версії означає «поле стерли», і показувати
  замість нього попередній запис не можна: людина бачить у своїй анкеті порожнє поле й
  очікує, що порожнє воно й для інших. `null` усередині масиву — не стирання, а
  пропущений індекс, яким SDK добиває дірки в даних бази: на ньому береться попередня
  версія. Історію бачить лише той, хто редагує анкету, — у формі лежить сире поле.
  Виняток один і він явний: **роль картки**, де масив це справді набір («і агенція, і
  донорка»), і збирає його `deriveRole`, а читає `listProfileRoles`. Правило деки
  читає як набір і ролі **читача** (`listViewerHiddenCardRoles`, див. вище), а
  «поточна — остання» (`resolveViewerCurrentRole`) лишилось для того, що справді
  питає одну роль. Різниця не випадкова: у картці питання «ким ця людина
  буває», і агенція з донорською анкетою лишається в стрічці агенцією; а в читача
  питання «ким вона зараз гортає», і після переходу з агенції в донорки `deriveRole`
  лишає їй `['ag', 'ed']` — прочитати це як набір означає не помітити зміни ролі взагалі.
  Через те саме `viewerRoleSignature` **не сортує**: із сортуванням `['ag','ed']` і
  `['ed','ag']` давали однаковий підпис, зміна ролі не читалась як зміна, і дека з чіпами
  лишались від попередньої ролі до перезавантаження сторінки.
- З того самого правила випливають чотири речі, які легко зламати назад:
  - порожній рядок, доданий у формі кнопкою «+», — це **намір**, а не значення:
    `appendEmptyFieldRow` кладе туди `undefined`, і писач знімає його перед записом.
    А біля коментарів «+» немає взагалі (`fieldAcceptsMultipleValues`): версій у
    них не буває — коментар один, його розширюють або звужують, правлячи той
    самий текст, — і дописаний другий рядок поїхав би в базу другою версією, а
    показувалась би скрізь лише остання.
    Поки «+» дописував `''` **і одразу зберігав**, скаляр ставав масивом з порожнім
    хвостом від самого лише дотику — тобто анкета «стирала» собі імʼя;
  - **картка стрічки мусить донести позначку стирання.** `collectFieldValues` знімає
    порожні значення, тож `['Оксана', '']` їхало в картку як `['Оксана']`, і рядок
    стрічки показував те, чого у відкритій анкеті вже немає. Тепер `projectionValue`
    дописує `''` назад, коли поточного значення немає, а `sameProjectionValue` цю
    різницю бачить — інакше писач вважав би картку незміненою. Зводити історію до
    поточного значення в картці **не можна**: `name` живе тільки в ній.
  - **похідна картки теж тримає історію, коли має куди.** `surnameShort` — це
    прізвище, скорочене до ініціала, і скорочуються **всі** версії:
    `['Коваленко', 'Марчук']` дає `['К.', 'М.']`, стерте — `['К.', '']`. Чистити
    там нічого: картка й так відкрита кожному авторизованому, а літера прізвищем
    не є (правило бази приймає і рядок, і список — межа довжини на кожному
    елементі). `rh` і `bloodGroup` — інша річ: це скаляри (у правилах на `rh` ще
    й `+`/`-`), позначці стирання лежати ніде, тож вони питають `hasCurrentValue`
    і при стертій групі крові ключа не пишуть — інакше стрічка фільтрувала б за
    «+» те, чого у відкритій анкеті вже немає. Те саме правило — у
    `flattenOwnerValueToString`: `join` знімає порожні елементи, тож стерта
    нотатка адміна (`['1 вересня', '']`) не переїжджає взагалі, а не їде живою.
  - **міграція з двох колекцій не воскрешає стерте.** `users` і `newUsers` зливаються
    в один список версій, і значення з `users` іде останнім (`mergeUserFieldValue`),
    тож стирання, записане в `newUsers`, опинялось усередині — і прибраний номер ставав
    поточним назад. Те саме робив і поріг порожнечі: копія, у якій лишився сам `''`,
    не переносилась узагалі. Тепер `saysFieldErased` питає обидві початкові копії, а
    `withErasureMarker` дописує позначку в кінець (звіт: `ERASURE_PRESERVED`).
- **Реакція записується одразу, а картку прибирає вже наступна дека.**
  `keepReactedUserIds` у `applyMatchingUiFiltersToUsers` тримає на місці ті
  картки, на які читач відповів у цьому ж перегляді; набір скидається, коли
  дека збирається заново (режим, фільтри). Досі лайк у відкритій картці гортав
  на наступну людину тієї ж миті — подивитись, кого щойно вподобав, чи
  виправити промах, було вже ніде, — а рядок списку випадав з-під свайпу.
  **Прибирань реакції три, і знати про набір мусять усі три**: фільтр показу
  (`applyMatchingUiFiltersToUsers`), збирач деки (`mergeMatchingCandidateUsers`)
  і ефект, який викидає картку з самого стану `users`. Поки виняток знали лише
  перші два, картка проходила крізь них і все одно зникала — до них вона просто
  не доходила. Те, що прибирало її з відкритої картки, звалось `handleRemove`;
  тепер той самий канал (`onReacted`) навпаки її **лишає**, і позначка ставиться
  **до** запису реакції, а не з її зворотного виклику: `onRemove` спрацьовує вже
  після того, як зміна списку вподобаних перемалювала сторінку.
- **Повернення до стрічки — це рядок, а не піксель.** Позиція відновлюється по
  `data-card-id` тієї картки, яку читач останньою дивився (`SCROLL_ANCHOR_KEY`,
  `findCardNodeById`), і спроба повторюється покадрово, доки рядок не
  з'явиться в DOM. Піксель лишається запасним. Сама по собі піксельна позиція
  не відновлювала нічого: дека повертається з кеша порціями, і `scrollTo` по
  ще короткому списку впирався в його кінець, знімаючи позначку «відновили»
  назавжди — людина, яка гортала до шістдесятої картки, поверталась на початок.
  Знайти рядок при цьому **мало**: найперша порція буває з однієї картки — і
  саме з тієї, яку шукали, — тож якір центрується щокадрово, а відновлення
  завершується аж тоді, коли кількість рядків не змінюється кілька кадрів
  поспіль (`SCROLL_ANCHOR_STABLE_FRAMES`). І **поки воно триває, списку не
  видно** (`$restoringScroll` на `FeedList` і `GalleryGrid`, саме `visibility`,
  бо місце список займати мусить): інакше читач бачить вершину списку, а за
  мить — стрибок на своє місце. Стеля очікування — `SCROLL_RESTORE_REVEAL_MS`:
  якоря могло вже й не бути в деці, і порожній екран гірший за неточну позицію.
  Порожній запис позиції при цьому не зберігається взагалі
  (`saveScrollPosition`): стрічка на початку й без переглянутої картки не важить
  нічого, а таким записом зносило рівно той орієнтир, з яким сюди збирались
  повернутись — у режимі розробки React ставить і знімає ефекти двічі, тож це
  ще й ховало саме відновлення від очей.
- **Знайдена картка мусить вести далі сама.** Рядок видачі пропонує три
  продовження й жодне з них не веде назад у пошук: відгуки (значок у ряду рішень
  просить їх прочитати), доповнення картки (олівець, `onEnrich` → форма
  створення зі `state.enrichCardId`) і «Створити нову» (чіп →
  `state.createFromQuery`).
  Обидві кнопки несуть **намір**, а не адресу екрана пошуку: раніше чіп вів на
  `create-profile` із `state.query`, якого той екран не читав, і читач шукав
  удруге те, що щойно знайшов. Форма доповнення читає картку тією самою
  воронкою (`readProfileFromNodes`) і показує її поля — «правкою» стає лише
  різниця з канонічним значенням (`buildOverlayFromDraft`), тож підставлене й
  не змінене не пише в базу нічого. Набраний **контакт** у нову картку
  підставляється лише тоді, коли пошук нічого не знайшов: зайняте значення
  перетворило б перше ж автозбереження на `DUPLICATE_PROFILE`. І знайдене
  більше не вимикає кнопку створення — дубль стереже зайнятість контакту в
  базі, а не вимкнена кнопка. **Закриття форми повертає до видачі**, а не на
  екран пошуку майстерні: адреса їде разом із наміром (`state.returnTo`,
  `utils/matchingSearchLocation.js`), а після перезавантаження сторінки
  береться з того ж сховища, з якого її читає рядок пошуку.
- **Заводити й доповнювати картки може кожен, хто увійшов.** Прапорець
  `canCreateProfiles` цього більше не стереже — ні в коді (маршрут
  `/matching/create-profile`, олівець `onEnrich`, заготовка у видачі), ні в
  правилах (`multiData/profileMutations/{автор}`, `profileIdentityClaims/{ключ}`,
  `multiData/edits/{картка}/{читач}` і обидва журнали). За ним лишились самі
  лише **службові читання цілих вузлів**: перелік усіх чернеток, усі шари однієї
  картки, перелік заявок на унікальність — тобто «створити» й «дописати»
  відкриті всім, а «подивитись, хто що створив і дописав» ні. Два замки при
  цьому лишились і без прапорця: **заявку на унікальність** (`profileIdentityClaims`)
  знімає чи перебиває лише той, чия картка за нею стоїть (інакше «створювати
  може кожен» означало б і «кожен може відвʼязати чужий номер і завести з ним
  дубль»), а **запис у журнал правок** приймається лише від того, чий шар на цій
  картці вже лежить — журнал читає адмін і вирішує по ньому, тож наповнити його
  записами про картку, якої не торкався, не можна. Гейт коштував
  рівно того, заради чого його ставили: акаунт без прапорця бачив чіп «Створити
  нову», натискав — і мовчки опинявся в «Моєму профілі», бо маршруту в таблиці
  не було. Свій шар читач тепер і читає сам (`multiData/edits/{картка}/{читач}`
  має власне правило читання) — вузол картки цілком лишається адмінові й
  службовому доступу. **Правила під це треба викотити руками**
  (`npx firebase deploy --only database`), інакше нові чернетки й шари падають
  на `PERMISSION_DENIED`; сценарії — `npm run test:rules`.
- **Дописане в доповненні мусить бути видно й знайдено.** Шар читача
  (`multiData/edits/{картка}/{читач}`) лягає на картку скрізь, де автор шару цю
  картку бачить — `getOwnOverlayFieldsForCards` + `applyOverlayToCard`.
  **Адмінові лягають шари всіх дописувачів, а не власний**
  (`getOverlaysForCard` + `applyOverlaysToCard`, `ensureStackedOverlay` у
  `Matching.jsx`): пише шар будь-який читач, а рішення по
  дописаному — адмінське, тож поки шар бачив лише його автор, адміністраторка
  єдина й дивилась на канонічну картку, тобто на все, крім того, заради чого
  відкривала. Ціну тримає той самий дотик: власного переліку доповнень в
  адміна немає й бути не може (шари лежать під картками, а не під ним), тож
  стрічку цим запитом не здорожчуємо — питаються видача пошуку й картка, якої
  торкнулись. Канонічне значення поруч із дописаним показує форма редагування
  (`EditProfile`: стос, підсвітка чужих правок і журнал
  `multiData/editsHistory`), а не рядок стрічки. Ціна різна:
  **видача пошуку** питає про кожну показану знайдену картку, **стрічка** —
  лише про ті, які назвав перелік власних доповнень
  (`multiData/editsByEditor/{читач}` плюс памʼять браузера,
  `utils/ownOverlayCardsStorage.js`), бо рядків у ній сотні. Перелік теж
  **потребує ручного викочування правил**; поки їх немає, лишається памʼять
  браузера — дописане в цьому ж браузері видно, з іншого пристрою ще ні.
  А ще шар питається **на дотик**: відкрита картка, розгорнутий рядок і
  натиснута трубка йдуть через `ensureFullProfile`, і той питає вузол цієї
  картки незалежно від переліку (`ensureOwnOverlayRef`). Перелік не всезнаючий
  — у базі він чекає на ручне викочування правил, а поза базою знає лише цей
  браузер, — тож без цього дописаний телефон було видно рівно в одному місці:
  у самій формі доповнення. Дотик стрічку не здорожчує: дотиків стільки,
  скільки їх зробила людина, а не скільки рядків у списку.
  Накладається шар **двічі** — на картку й ще раз після `ensureFullProfile`:
  анкета приїжджає такою, якою її бачать усі, і накривала б собою дописане
  рівно тоді, коли контакти й читають. Значення з шару йдуть і в `searchId` —
  на картку, одразу після запису шару (`saveOverlayForUserCard`); право на цей
  запис дають правила за наявністю самого шару, тож **без ручного викочування
  правил дописане не індексується** (`docs/searchId-index.md`). Прибране в шарі
  з індексу не знімається: це ще не стирання в анкеті.
- **Пропозиція редактора — це значення, а не поле.** Шар зберігає зміну поля
  цілком (`{ phone: { added: ['A', 'B'] } }`), і форма адміна показувала її
  одним рядком: два дописані номери зліплювались у «A, B» в одному інпуті
  (`sanitizeOverlayValue` робив з масиву рядок). Звідси йшло дві поломки
  поспіль — «ОК» записував той склеєний рядок в анкету як один номер, а «×»
  зносив геть увесь шар поля, тобто й друге значення, якого адмін не чіпав.
  Тепер розкладає пропозиції одне місце на всі екрани —
  `buildOverlayFieldEntries` у `utils/multiAccountEdits.js`, по рядку на
  значення з автором, — а рішення приймає `settleOverlayValueForCard`:
  вирішене значення йде з шару, решта лишається (`settleOverlayFieldValue`),
  і **відхилене знімається ще й з `searchId`** — ключ туди завів сам шар
  (`saveOverlayForUserCard`), і поки він там лишався, прибраний номер далі
  знаходився пошуком. Знімається не завжди: якщо значення стоїть в анкеті або
  його пропонує ще один редактор, ключ лишається — він веде на картку, а не
  на шар. Прийняте значення з індексу не знімають узагалі: воно щойно поїхало
  в анкету.
- **Історія пошуку читача — це слід його роботи, і адмінка вміє на нього
  подивитись.** Кнопка «🔎 Хто шукав» (група «Добірки») на `AddNewProfile` читає `multiData/searchQueries`
  цілком (`fetchAllSearchQueryOwners`; правило `.read` на вузол — адмінське,
  тобто **потребує ручного викочування**) і малює картки самих читачів, а під
  кожною — її запити (`renderCardFooter` у `UsersList`). Натиснутий запит іде
  тим самим шляхом, що й набраний у рядку: значення лягає в `search`, а
  `SearchBar` перемонтовується й виконує його на старті. Номер у тому списку —
  контакт, а не текст: поруч стоять Telegram, Viber і WhatsApp
  (`CONTACT_LINK_BUILDERS.*FromPhone`), бо питання «хто це шукав» одразу тягне
  за собою «напишіть йому». Читання дороге (вузол цілком), тож воно на явне
  натискання, а фільтри картотеки цей перелік не звужують і не пересортовують —
  це відповідь на інше питання, а не зріз стрічки.
- **Шар тримає поточну правку, журнал — усі попередні, і адмін бачить обидва.**
  Шар редактора (`multiData/edits`) — це різниця з карткою, і кожне збереження
  його переписує: читач замінив номер на А, поправив А на Б — у шарі лежить
  самий Б. А лишалось лише в `multiData/editsHistory`, якого форма адміна
  (`ProfileForm` на `AddNewProfile`) не читала, тож першої правки адмін не бачив
  узагалі. Тепер журнал розкладається назад у пропозиції
  (`buildSupersededOverlayEntries`): рядок із підписом «Попередня версія
  правки», і рішення про нього (`settleSupersededOverlayValue`) чистить журнал,
  а відхилене знімає ще й з `searchId`. **Рішення адміна слідів не лишає**:
  `settleOverlayValueForCard` більше не дописує в журнал «accept»/«discard», а
  знімає записи про розсуджене значення — звіряючи з тим, що зміна
  **пропонує** (`changeProposalValues`), а не з її `from`: дві правки поля
  мають спільний `from`, і звірка з ним зносила б і попередню версію. Запис
  журналу — це одне збереження поля, тож він буває з кількома значеннями
  (`{ added: [A, B] }`); рішення про A такий запис **переписує** з рештою
  значень (новий ключ, той самий автор і `at`), а не зносить — інакше B зникав
  із попередніх версій разом із чужим рішенням. Частково правити запис
  правила не дають: його можна лише створити або (адмінові) видалити. **Шар,
  що дублює картку, знімається сам** (`pruneOverlaysMatchingCanonical`, на
  відкритті картки в `ProfileForm`): значення вже в анкеті — пропонувати нічого.
- **Фото картки гортаються свайпом у рядку й у плитці галереї** (`usePhotoSwipe`).
  Проєкція стрічки несе один аватар, і решту переліку просить **сам жест**:
  перший свайп кличе `requestCardPhotos` у `Matching` — одне читання на картку,
  по якій провели пальцем, а не лістинг Storage на всю сторінку наперед. Жест
  на фото належить фото (`stopPropagation`): свайп рядка ставить реакцію, і
  гортання знімків не має ставати серцем чи хрестиком.
- **Розсуджує дописане одне місце — черга доповнень на `AddNewProfile`**
  (кнопка «Доповнення», `AddNewProfileOverlayReview.jsx`). Доти рішення по шару
  ухвалювали, лише **випадково** відкривши ту саму картку: шар лежить під
  карткою, оберненого індексу «картка → є шар» немає й бути не може, тож черга
  читає корінь `multiData/edits` цілим вузлом (`listPendingOverlayCards`).
  `.read` на цьому корені має рівно **адмін** — кому відкрито корінь, тому
  відкрито «хто кого дописував по всій базі», а це вже не «доповнити картку».
  **Правила під це треба викотити руками** (`npx firebase deploy --only
  database`), і доти черга показує не порожнечу, а причину: «доповнень немає»
  бреше рівно тоді, коли їх найбільше. Рішення там на **значення**, а не на
  картку: із трьох дописаних телефонів правильний буває один, і «прийняти все»
  записало б у картку два чужі номери. Розкладає пропозиції й ухвалює рішення
  той самий код, що й у формі редагування — `buildOverlayFieldEntries` і
  `settleOverlayValueForCard`, — тож відхилене йде і з `searchId`, а не лише з
  екрана. Прийняте значення пише в анкету `utils/persistCanonicalCard`
  (спільний з `EditProfile`) — і пише **до** settle: шар після нього вже не
  існує, і записане після нього не лишило б сліду ніде. Заміна при цьому
  лишається заміною (`{ from, to }`), а не другим значенням поруч зі старим:
  зведена до `added`, вона дала б в анкеті «Київ, Львів» замість «Львів».
- **Список «кому дзвонити» питає вузол власника, а не глобальний індекс.**
  `getInTouch` — позначка **того, хто її поставив**: вона лежить у
  `multiData/getInTouch/{власник}/{картка}` **значенням**, і правила оголошують
  на ній `".indexOn": ".value"`. Тому порядок і межу дати робить база —
  `orderByValue() + endAt(сьогодні) + limitToLast(сторінка + 1)`, один запит на
  сторінку (`collectOwnerGetInTouchCandidateIds`). Доти те саме питалось
  `searchKey/getInTouch`, де дата сидить у **назві** денного бакета: діапазон по
  ній не береться, тож код ішов календарем по одному дню за круг — до 45 днів на
  батч і до 25 батчів на сторінку, і порожній день коштував рівно стільки ж,
  скільки заповнений. Одна сторінка з двадцяти карток могла впертись у понад
  тисячу **послідовних** кругів. Заразом зникла розбіжність: той індекс
  глобальний і зберігав чиюсь чужу позначку, а показує екран завжди позначку
  читача (`readProfileFromNodes` бере її з мапи власника). Гортання назад
  просить **не зсув, а курсор** — пару (значення, ключ) останнього відданого
  рядка через `endBefore`: зсув з'їхав би, бо між сторінками адмін ставить і
  знімає позначки, а однакові дати інакше або задвоюються, або гублять хвіст.
  Рядок понад сторінку питається лише щоб відповісти на «чи є далі» — у видачу
  він не їде, інакше приїхав би вдруге вже наступною сторінкою. Дві пастки, які
  легко повернути: **обʼєкт при `orderByValue()` сортується після всіх
  скалярів**, тож стара, перевернута форма запису (`{власник}/{значення}/
  {картка}: true`) під межу «не пізніше сьогодні» не потрапляє **взагалі** — її
  ловить проба на один рядок (`ownerGetInTouchHasLegacyGroups`), і такий вузол
  далі гортається з мапи; а `searchKey` лишається **тільки** пост-фільтром
  (`filterIdsBySearchKeyPointGroups` до гідратації, `filterMain` після) — тобто
  сортування ним більше ніде не робиться. І окремо: **`forEach` знімка
  перериває обхід, щойно колбек вернув truthy**, тож колбек тут мусить мати
  блокове тіло — стислий `child => rows.push(…)` вертає нову довжину масиву,
  тобто `1`, читає рівно перший рядок, і виглядає це не як поломка читача, а як
  порожня база.

- **Порядок стрічки на `AddNewProfile` береться зі стрічки.** Кнопка «Стрічка»
  показує картки так, як їх бачить читач на `/matching` — за `feedDate` (він же
  `lastLogin2`), — і робить це тією самою `fetchMatchingCardsPage`. Своя
  сортувалка тут була б другою реалізацією тієї самої пагінації й розійшлася б
  зі стрічкою при першій же зміні в ній. Курсор у неї — пара (дата, id), і
  лежить він у `feedCursorRef`, а не в стані: ефект перезавантаження читає стан
  зі свого замикання, тож щойно скинутий `lastKey` приїхав би туди старим — і
  перша сторінка починалася б із середини стрічки (та сама причина, що й у
  `dateOffset2Ref`).
- **Кнопки `AddNewProfile` розкладені по групах, а не одним килимом.** Панель
  (`ConsolePanel` у `AddNewProfileAdminPanel.styled.jsx`) має пʼять груп —
  список, добірки, індексація, дані, сервіс, — і кожна кнопка називає дію
  словом. Доти два десятки однакових прямокутників («Info ClearCache ІЛ Load ⚙
  🧾 ❤ 👤 Індекси Картки 🔎Хто TG💬 ID💬 DPL Save Merg XLSX JSON») стояли поспіль, і
  «Очистити кеш» виглядала так само, як «Картки» — тобто як перебудова вузла на
  всю колекцію. Тому в кнопок є тон: `danger` носить те, що пише в базу цілим
  вузлом або незворотно міняє дані. Вхід у **окремий екран міграції**
  (`/rtdb-migration`) стоїть у групі «Дані», а звідти назад веде «← До панелі
  анкет»: екрани різні, робота одна, і памʼятати про меню «⋮» більше не треба.
- **Над видачею пошуку немає нічого, крім самої видачі.** Чіпів пошуку три й
  усі пішли: «Знайдено N» повторювало довжину списку під ним, «Створити нову»
  дублювало заготовку першим рядком, а «Схожі» пропонували другу відповідь на
  той самий запит із локального кеша — того самого, який правом показу не є.
  Рядок стану лишився для двох станів, на які подивитись нема куди: пошук
  триває і пошук упав. «Знайшов у searchId: 380505554433» не казало нічого —
  що знайшлось, видно зі списку, а що ні — з порожнього списку й заготовки.
- **Перший рядок видачі — заготовка нової картки.** Набране розкладає той
  самий `detectSearchParams`, що й пошук (нерозпізнане він називає імʼям), і
  та сама кнопка веде у форму створення, що й чіп «Створити нову». Зайняте
  знайденою карткою значення заготовка називає зайнятим — підставити його в
  нову картку означало б відповісти людині `DUPLICATE_PROFILE` замість форми.
- **Коментарі — це два різні сховища, і плутати їх дорого.** Особиста нотатка
  адміна до картки лежить у `multiData/comments/{ownerId}/{cardId}` і видна лише
  власникові; публічний відгук про людину — у `comments/{profileId}/{commentId}`,
  підписаний автором і відкритий кожному авторизованому. Картки, заведені імпортом
  з таблиці (id виду `TG0001` і `ID0001`), отримали відгук агенції в **нотатку**,
  тож його переносять кнопки «TG💬» і «ID💬» на `AddNewProfile`
  (`utils/legacyImportCommentMigration.js`; партія — це параметр-префікс, а не
  друга копія коду).
  Три рішення там навмисні: автора в базі немає, тож `authorId` синтетичний і
  виведений з імені (`writer`) — той самий автор дає той самий id (і в обох
  партіях, тому партії в цьому id немає), а повторний запуск не вигадує нової
  людини; уже перенесений відгук упізнається за текстом і
  вдруге не пишеться; приватний оригінал прибирається лише **після** вдалого
  публічного запису. Записати відгук від чужого імені дозволено самим лише адмінам —
  і дозволено це `database.rules.json`, тобто **правила треба викотити руками**,
  інакше перенос упаде на `PERMISSION_DENIED` (звіт це називає прямо, разом з
  командою деплою, — «перенесено 0/N» без причини вже коштувало одного розбору).
  **Доказ походження є не в кожної партії.** Нотатку публікує те, що вона лежить
  у піддереві імпортера **і** має автора. TG-картки мають позначку `writer`, а
  партія з таблиці (`handleExcelProfilesUpload`) записує картку, коментар і
  дизлайк — і жодного `writer`. Автора такій партії дає вона сама
  (`LEGACY_IMPORT_BATCH_WRITERS`: `ID` → «ID»): походження там доводить саме
  піддерево імпортера — особисті нотатки адміністраторки живуть під її власним
  uid, якого міграція не читає взагалі. Своя позначка картки сильніша за
  партійну й перебиває її. Партія без запису в цій мапі лишається під гейтом, і
  знімає його не код, а людина: `confirmMissingWriter` показує самі тексти й
  питає, чи публікувати їх, і лише після «так» ставиться `allowMissingWriter`. Мовчазний прогін (без цього запитувача) і далі не
  публікує нічого неперевіреного, а звіт називає, скільки саме відкинуто: «не
  знайдено» там, де 25 нотаток відсіялись гейтом, вже коштувало одного розбору.
  **Межі довжини дві, і це навмисно:** 2000 знаків для того, хто пише коментар
  зараз, і 10000 для адміна (`PUBLIC_COMMENT_ADMIN_MAX_LENGTH`) — бо перенос не
  пише новий текст, а рятує вже написаний: обрізати його означає загубити
  частину відгуку, а розрізати надвоє — вдати, що авторка писала двічі. Обидві
  межі стоять і в коді (`resolvePublicCommentMaxLength`), і в правилах.
  Тим самим шляхом порівняння
  дублікатів переносить відгуки між картками (`copyPublicCommentsBetweenCards`):
  раніше вони лишались на картці, яку закривають. У блоці картки
  (`renderTopBlock`) обидва сховища стоять одним списком — під нотатками інших
  адмінів ідуть публічні відгуки, — і саме тому відгук мусить лишатись помітно
  іншим (глобус, зелена смуга, імʼя автора, окремий заголовок модалки): рядки
  сусідні, а наслідок правки різний. Відгуки там приїжджають **разом із
  карткою**, а не на дотик: кнопка лишилась одна — на повтор після відмови, — а
  ціну читання тримає памʼять таба (`docs/matching-feed-traffic.md`, «Рівень 3»).
  «Ваш коментар» у формі доповнення знайденої картки — теж **нотатка**
  (`FieldComment`, `multiData/comments`), а не поле оверлея: підпис мусить
  означати одне й те саме скрізь, а «що варто знати адміністратору» пояснювало
  шлях запису замість того, щоб назвати річ.
  У стрічці все навпаки: там рядок гортають повз десятки анкет, і читання й далі
  коштує рівно стільки разів, скільки натиснули значок відгуків у ряду рішень.
- **Рядок стрічки закінчується рішенням, і рішення це один ряд.** Порядок у
  картці сталий: шапка (фото, імʼя, роль і локація) → метрики й факти →
  «Детальніше» (розгорнуте лягає просто під кнопку) → контакти → нотатки →
  ряд рішень. У самому ряду (`RowFooterActions`) порядок теж сталий: хрестик →
  серце → олівець. Розгортання стояло стрілкою в правому кінці ряду, і до
  нього треба було тягнутись у куток екрана; тепер це слово «Детальніше»
  посеред картки (`RowDetailsToggle`), а на місце стрілки став олівець, який
  до того стояв угорі біля імені. Кнопки «Контакти» тут немає: контакти стоять у картці
  самі, одним рядком значків, і підтягуються без дотику (див. «Контакти — один
  рядок значків» нижче). Плитка
  галереї несе той самий ряд (`RowReactionPair`) і ту саму смугу показників
  (`ProfileStatStrip`) замість власного курсивного «178/88 | BMI». **Лайк завжди праворуч від дизлайку** — у рядку, плитці
  галереї, відкритій картці й шапці чернетки однаково; у рядку це тримає
  порядок `primaryAction` (хрестик) → `secondaryAction` (серце), який передає
  `Matching`. Той самий ряд рішень стоїть і в списку прихованих
  (`buildRowExtras` → `buildHiddenRowExtras`): прихована картка — не архів, у
  якому нічого не можна, читач заходить туди саме щоб згадати, що́ сталося, і
  там же вирішити; поки рядок пропонував одну кнопку «повернути», звірити
  номер чи перечитати відгуки можна було, лише спершу повернувши анкету в
  стрічку. Олівець при цьому один на обидві ролі **й на обидва екрани**: у
  відкритій картці (`editProfileAction`) його адмінові не було зовсім, і жест,
  який діяв у списку, вів у нікуди. Серце з хрестиком стоять у спільній рамці (`RowReactionPair`):
  це два боки одного вибору, а порізно вони читались як два незалежні значки.
  Написів у ряду немає — їх несе `title`/`aria-label`: широкі рядки «Доповнити
  дані» й «Перевірити наявність відгуків» разом зі стовпчиком значків праворуч
  давали три місця для рішень про ту саму людину й пів екрана на картку з трьох
  фактів. Олівець один на обидві ролі: не-адмін ним дописує знайдену картку
  (`onEnrich`), адмін відкриває її на редагування (`onEditProfile`).
- **Рядок стрічки починається з фото, і воно на всю ширину картки.** Плиткою
  52 px збоку від імені фото не показувало нічого, а розкладок списку було три:
  рядок, дві колонки й «одна картка на екран» — остання й існувала лише заради
  великого знімка, але під ним стояли три факти й пара кнопок, тобто цілий
  екран за менше, ніж каже рядок. Її прибрано, велике фото переїхало в рядок
  (`Photo` у `MatchingHiddenList.styled.jsx`, портретні 4/5 зі стелею висоти),
  а потім пішла й галерея: плитка показувала ту саму картку урізаною, і
  розкладка стрічки тепер одна — список (`MATCHING_VIEW_LAYOUT`), без
  перемикача. Не повертайте другу розкладку «для компактності».
- **Рядок стрічки й відкрита картка донорки складаються з тих самих частин**
  (`components/ProfileFacts.jsx`), і верх відкритої картки — дослівно той
  самий блок, що рядок списку. Частин три: смуга показників
  (`buildProfileStatStrip`: зріст, вага, ІМТ, кров — чотири комірки в сталому
  порядку, відсутнє — тире, а не зсув колонок), короткі факти
  (`buildProfileSummaryRows`: «Зовнішність — карі очі, русяве волосся»,
  «Пологи, донації — двоє пологів, останні 18 міс тому · 1 донація»,
  «Сімейний стан — не заміжня») і розділи повної анкети
  (`buildProfileDetailSections`: обличчя й фігура, освіта й робота, розміри;
  разом із «Про себе» — `ProfileAboutSection`). **Перші дві частини беруть лише
  поля картки `matchingCards`**: рядок показує їх без жодного читання і не
  міняється, коли приїхала повна анкета, — вона лише уточнює на тих самих
  місцях прізвище й групу крові («Rh+» → «O+»). Поле, якого в картці стрічки
  немає (структура волосся, освіта), у короткий блок не кладеться — його
  місце в розділах; `ProfileFacts.test.js` звіряє блок із картки стрічки з
  блоком повної анкети. Розділи показують розгорнутий рядок (стрілка
  розгортає, клік по картці відкриває) і відкрита картка; інші ролі у
  відкритій картці поки на своїх секціях (`getProfileSections`). Підпис

- **Стрілка «всі дані» числа біля себе не несе.** Воно там було й брехало:

- **Ліва межа картки одна, і вкладених плашок у рядку немає.** Усе, що нижче

  контакти, «всі дані» й нотатки. Заокруглені плашки з підкладкою
  (`--matching-inset-bg`) там були й пішли разом із самим токеном: рядок сам по
  собі вже заокруглена картка з фото на всю ширину, і вкладена в неї друга
  заокруглена коробка з іншим фоном читалась наліпкою. Смужка доріжки нотаток

  відступі картки, а не на її краю, тож зі смужкою ролі не зливається. Спроба

  колись мовчки клала її під власну рамку картки — не повторюйте. У **відкритій** картці плашка
  (`ModernSection`) навпаки доречна: та картка на екрані одна, і плашка ділить
  її на блоки. Метрики теж стоять під шапкою, а не в колонці поруч із фото: там

- **Відгуки й власна нотатка — одна плашка, дві підписані доріжки**
  (`ProfileNotes` у `ProfileRow`: `RowNotes` плюс `NoteLane` з розкладки
  відкритої картки), і публічне стоїть **над** власним: відгук читають, а
  нотатку пишуть, тож відповідь мусить бути над полем для питання. Плашка стоїть
  **у кожній картці будь-якої розкладки** — рядок стрічки, плитка галереї,
  список прихованих, відкрита анкета (`NoteLanes` у `Matching.jsx`): розкладка
  міняє те, як картку показують, а не те, що про людину вже записали.
  **У стрічці порожня доріжка згорнута** в пару кнопок «Відгук» / «Памʼятка»
  (значок і слово кольором доріжки на тонованій підкладці, як ряд рішень)
  (`hasPublicContent`/`hasPrivateContent` у `ProfileNotes`): шістдесят
  порожніх полів на сторінку робили кожну картку довшою за екран телефона.
  Написане видно без дотику — доріжка розгортається сама, щойно в ній є
  відгуки (прапорець чи прочитані), стан їх читання або власна памʼятка, тож
  дописати поверх запису, якого не бачиш, не можна. Відкрита картка й форма
  тримають обидві доріжки розгорнутими, як і раніше.
  **Поле не сховане за читанням.** Публічну доріжку колись відкривала кнопка
  «перевірити відгуки» — тобто написати відгук можна було лише дорогою до
  чужих. Тепер жест просить саме **читання**: значок у ряду рішень
  (`reviewsAction`) робить один запит, а поле для власного запису читань не
  потребує — воно пише. Через це порожня доріжка вже не означає «ще не
  читали», і стан читання каже словом `describeReviewsState` («Шукаємо
  відгуки…», «Не вдалося прочитати відгуки») — інакше невдале читання
  виглядало б як «відгуків немає». Підпис над доріжкою і плейсхолдер беруться
  з `profileTexts`, а не з рядка в коді, і вони **одні на всі екрани**:
  «Публічний відгук» / «Додати анонімний відгук» і
  «Памʼятка для себе» / «Додати памʼятку». Третього рядка («Бачите тільки
  ви», «Бачать усі») немає: з підписом і плейсхолдером це були три однотипні
  сірі написи про одне. Смужка доріжки — акцентна в відгуку, зелена в
  памʼятки (`NOTE_LANE_*_COLOR`); поля — текст без рамки інпута скрізь, і
  записане знімає один хрестик (`NoteClearButton`, мішень 28 px) — і під
  відгуком, і біля памʼятки, без другого кроку «Видалити?». **Відгук
  анонімний**: імені чи ініціалів автора під ним немає, і нові відгуки
  `authorName` не пишуть узагалі (лишається `authorId` — його вимагають
  правила, щоб автор міг свій відгук правити й знімати). Нотатку видно **всім показаним карткам** —
  `loadCommentsFor(feedRows, { activeOnly: false })`, один запит за піддеревом
  власника, — інакше читач дописував би поверх власного запису, якого не бачить.

  (`utils/profileNormalization.js`). У базі Україна записана вісьмома способами
  («Украина», «Ukraine », «УкраЇна»…), області й міста — українською, російською й
  англійською впереміш, а частина анкет з-за кордону має зріст у футах: рядок
  стрічки казав «Славянск, Донецкая обл.» і «5/3 BMI 1200». Довідник знає
  конкретні назви й показує їх мовою інтерфейсу; незнайоме лишається як написали
  — це не переклад вільного тексту. Неправдоподібний зріст, вага чи ІМТ не
  показуються зовсім. Фільтр країни й бакет ІМТ (`searchKeyBuckets`) питають ті
  самі функції, що й показ, — інакше фільтр «Україна» не впізнавав би частини
  українських анкет. На збереженні (blur) «Мій профіль» і власна чернетка
  записують знайоме канонічною українською назвою; у доповненні — ні, бо
  нормалізоване значення лягло б у шар правкою, якої читач не робив.
- **VK у формах не пропонується** (`MyProfile`, `ProfileCreationWorkspace`):
  мережа заблокована в Україні, і поле для неї читалось як знак, чий це
  застосунок. Записані значення лишаються в анкеті, індексі й адмінці.
- **Висоту фото у відкритій картці задає пропорція знімка, а не частка екрана.**
  46% висоти при повній ширині — це горизонтальна смуга, а всі знімки в анкетах
  портретні, тож `cover` зрізав усе нижче очей: у картці лишалось чоло.
  `ModernHero` тримає портретні 4/5 — ту саму пропорцію, що й фото в рядку
  стрічки, — зі стелею, щоб на високому екрані під фото лишались мініатюри,
  імʼя й метрики. Вікно кадру стоїть на 24%, а не по центру: у портреті центр —
  це вже плечі.
- **Публічна нотатка й приватна стоять парою скрізь, зокрема у формі чернетки
  й доповнення.** Там вони жили в двох різних місцях екрана: публічний коментар
  — останньою секцією форми, приватна нотатка — у шапці чернетки (а в
  доповненні ще й окремою плашкою «Ваш коментар»), тобто два записи про ту саму
  людину читались як дві незвʼязані речі. Тепер це ті самі `NoteLane` з
  розкладки стрічки, у тому самому порядку (публічне зверху) і з тими самими
  підписами й плейсхолдерами з `profileTexts`. Дві пастки: смужки доріжок
  потребують **запасних значень** змінних (`var(--matching-accent, var(--km-accent, …))`)
  — форма живе поза матчингом, де `--matching-*` не оголошені; а приватну
  нотатку малює чужий компонент (`FieldComment`), тож екран передає йому
  `ClearButton` — той самий `NoteClearButton`, — а оболонка `NoteFieldShell`
  знімає з поля все, крім тексту: пара мусить виглядати так само, як у стрічці.
  Дата в полях цієї форми показується й набирається як `дд.мм.рррр`, а в базу
  їде в `РРРР-ММ-ДД` — перелік полів-дат один на всі форми
  (`PROFILE_DATE_FIELDS` у `utils/profileDate.js`).
- **Форма адміна читає й пише чернетку як чернетку** (`utils/profileRecordSource.js`).
  У чернетки немає вузлів готової анкети — є запис
  `multiData/profileMutations/{автор}/{картка}` і журнал
  `multiData/profileMutationHistory/{картка}`, — а `AddNewProfile`, `EditProfile` і
  `ProfileForm` знали лише вузли: «усі поля» (`refreshCardFromBackend`, звідки
  бере дані `renderAllFields`) питали `fetchUserById`, отримували `null` і лишали
  на екрані старий знімок з кеша; збереження йшло в `updateProfileNodesInRTDB`,
  тобто заводило поруч із чернеткою напівготову картку, а чернетка й її журнал
  правки адміна не бачили; історію форма брала лише з шару редакторів, де правок
  чернетки немає; посилання «Контакти» вело в `profileContacts/{id}` = `null`.
  Тепер розгорнута чернетка несе адресу джерела (`__profileMutationCreatedBy`,
  `__profileMutationRevision` — `expandProfileDraft`), читання йде через
  `fetchProfileRecordById` (вузли, а без них — чернетка; з `prefer: 'draft'` —
  одразу її адреса), запис — через `saveDraftProfileRecord` (той самий
  `saveCreateProfileMutation`, що й в автора, тобто ревізія й журнал), а
  `getCanonicalCard` без жодного вузла віддає чернетку — тож і прийняте
  доповнення (`persistCanonicalCard`) лягає в неї. Збереження форми йде лише
  поверх ревізії, яку форма показувала (`knownDraftRevisions`): чужа новіша
  ревізія — відмова з поясненням, а не тихе затирання правки автора. Особисті
  позначки адміна (`getInTouch`, `writer`, `myComment`) у дані чернетки не
  потрапляють. Журнал чернетки адмін бачить у `ProfileForm` («Історія змін
  чернетки»).
- **Під формою адміна — «Усі дані картки в базі»** (`ProfileDataTree`,
  перелік місць — `utils/profileDataTree.js`): вузли анкети, позначки власника
  (зокрема графік стимуляції), чернетка з журналом, шари доповнень, відгуки,
  програми, ключі `searchId`, а для акаунта ще й його власні вузли (ліниво).
  Кожен вузол підписаний шляхом і веде в консоль; запис іде прямо за адресою,
  як у консолі, і похідних (картка стрічки, індекси) не перебудовує. `users/{id}`
  стоїть самим посиланням — legacy не читається. Новий per-card вузол додавайте
  в цей перелік, інакше адмін його не побачить. Графік стимуляції форма не
  показувала зовсім: `readProfileFromNodes` дочитував із `multiData` лише
  `getInTouch` і `writer` — тепер і `stimulationSchedule`.
- **«Очистити все» в чернетці не видаляє її, а стирає** (`clearAllDraftFields` у
  `ProfileCreationWorkspace`): кожне заповнене поле стає порожнім рядком одним
  збереженням, тож журнал правок лишає адмінові все стерте, а заявки на
  унікальність звільняються. `searchId` не чіпається — старий номер і далі веде
  на картку, — тому порожню чернетку ховає кожен показ, крім адмінського:
  список «Мої картки», стрічка (`personalCreateProfiles`) і видача пошуку
  (`readProfileDraftForSearchHit`). Умова одна — `hasFilledProfileDraftData`
  (`utils/profileDraftContent.js`), і питає вона **поточне** значення.
- **Стан чернетки називає лише те, що справді міняється.** Чіп «Очікує
  підтвердження» обіцяв гейт, якого немає: заведена картка вже лежить у пошуку,
  її знаходять, читають і пишуть під нею публічні відгуки. Лишились «Спільна
  чернетка» й «Приватний».
- **Прочитана порожнеча відгуків мовчить.** `describeReviewsState` говорить
  лише про читання, яке триває або впало. Рядок «Публічних відгуків ще немає»
  тут був, але відгуки тепер приїжджають самі, і він лише займав місце в
  кожній картці. Так само пішли «Анкета не заповнена» й «Додаткових даних
  немає»: порожній блок «всі дані» не малюється зовсім (`hasMoreDetails` у
  `ProfileRow`). Кегль рядка стану — підписний (`NOTE_META_SIZE`), а не
  текстовий: під плейсхолдером однаковий кегль робив із двох сірих рядків два
  запрошення написати.
- **Чіп фільтра стрічки обирає, а не вимикає** (`toggleFilterOption` з
  `selectOnly` у `CheckboxGroup`). Із незайманої групи дотик до «не заміжня»
  лишає саму «не заміжня»; далі дотики додають і знімають по одному, а зняте
  останнє повертає групу в незайманий стан. Картотека адміна лишилась на
  відніманні. Під фільтрами порція рахується картками **після** фільтрів:
  джерело дочитується, доки сторінка не набереться або не скінчиться
  (`collectFilteredMatchingSourceCards`).
- **Пошук — окремий крок історії.** Перший символ запиту кладе запис
  `matchingSearch` (`searchHistoryEntryRef` у `Matching.jsx`), і «назад» телефона
  з видачі стирає запит і повертає стрічку, а не виводить зі сторінки. Відкрита
  картка кладе свій запис поверх, тож «назад» у ній закриває картку, а пошук
  лишається. Стертий вручну запит знімає свій запис `history.back()`.
- **Кнопки колекцій — значки реакцій картки**: «Усі», хрестик, серце, у тому
  самому порядку й рамці, що й ряд рішень (`CollectionButton`).
- **«Мій профіль» питає мовою ролі** (`utils/myProfileRoleTexts.js`): агенція
  й клініка бачать «Назва агенції/клініки» й «Контактна особа» замість «Імʼя»
  й «Прізвище», біологічні батьки — «Кого шукаєте»; «Спосіб життя» з одним
  «Про себе» в не-донорки зветься «Про себе». Поля в базі ті самі (`name`,
  `surname`, `moreInfo_main`) — міняється лише підпис, тож картка й пошук їх
  не помічають. Підказки пишуться як «Наприклад: …»: сірі «Марія Іваненко»
  виглядали як уже введене. Спільний `pickerFields` тут не чіпається — з нього
  малює десяток інших екранів. «Очистити анкету» стоїть у меню «⋮» поруч із
  «Видалити анкету» (`onClearProfile` у `ProfileDotsMenu`), а не під
  «Опублікувати», де до незворотної дії був один промах пальцем.
- **«Приховати» більше не означає нічого — у кожної дії своє слово.** Хрестик
  на картці — «Не цікаво» (колекція «Не цікаві», повернення — «Повернути в
  «Усі»»); цятка адміна й «Мій профіль» — «Зняти з публікації» /
  «Опублікувати», статус «Не опублікована». Одне слово на три різні дії
  («не показувати мені», «зняти для всіх», «сховати мою») і стало причиною,
  з якої адмін вважав цятку зламаною.
- **Повернене з колекції стоїть на початку «Усіх»** до перезавантаження
  (`utils/matchingReturnedCards.js`). Зняття реакції картку в деку не вертає —
  вона стає за датою публікації, тобто для старої анкети за кілька сторінок, і
  людина казала «не повертається». Повернення ловиться за зміною мап реакцій
  (а не в обробнику: зняти лайк можна з рядка, плитки й відкритої картки), а
  піднімається двічі — до злиття деки й після нього, бо чернетки за датою й
  надані картки ставали над ним. У самій колекції картка зі знятою реакцією
  лишається до виходу з неї (`stickyReactedUserIds` у `reactionTabUsers`). Стрілка «розгорнути» в рядку одна — у ряду
  рішень; смужка публічної доріжки червона (`$reviewed`), коли під карткою
  прочитано хоч один відгук.
- **Плашка ролі в галереї лежить на фото**, у лівому верхньому куті — той
  самий `PhotoRoleBadge`, що й у рядку; без фото роль стоїть біля імені
  (`RoleCode`), як у рядку однієї колонки.
- **Публічний відгук публікує кнопка, а не втрата фокуса** (`CommentComposer` у
  `ProfileRow`). Поле відгуку й поле памʼятки виглядають однаково, а наслідки
  протилежні, і поки відгук ішов у базу на blur, на телефоні його публікувала
  прокрутка. Тепер під полем — «Побачать усі користувачі» і кнопки «Опублікувати»
  / «Не публікувати» (Ctrl+Enter теж публікує); blur лише згортає порожнє поле.
  Памʼятка лишається на автозбереженні. Роль автора під відгуком потребує поля в
  `comments/{id}/{commentId}`, а там `$other: false` — тобто ручного деплою правил.
- **Контакти у відкритій картці стоять першими під шапкою**, і до них веде трубка в
  ряду дій (`openContactDetails`). Блок жив у самому низу, під анкетою й нотатками.
- **Повна група крові — у картці лише опублікованої анкети** (`resolveCardBlood`,
  `MATCHING_CARD_MIRRORED_FIELDS`). Рядок стрічки показував сам резус («Rh+»), і
  читач не розумів, яка це група. Картку ж бачить кожен авторизований, зокрема
  неопубліковану, яку знаходить пошук, — тож `blood` лежить у ній рівно доти,
  доки є дата в `feedDate`, і правило бази вимагає того самого. Картки,
  опубліковані до цього, дописує разова робота «Група крові в картках» на
  панелі індексації `AddNewProfile` (`backfillMatchingCardBlood`). **Правила
  треба викотити руками**; доти `syncMatchingCardIndex` пише картку без `blood`.
- **Зона контактів підписана й велика**: заголовок «Контакти», дзвінок —
  заповнена кнопка «Подзвонити», мішені 40 px, месенджери у своїх кольорах
  (`CONTACT_CHANNEL_COLORS`). Сірі рамки 28 px без підпису користувачі не
  помічали.
- **Контакти — один рядок значків, скрізь однаковий** (`ContactLinks` у
  `ProfileRow`: рядок стрічки, відкрита картка, список прихованих, шапка
  чернетки й доповнення, прев'ю «Мого профілю»). Трубка — це дзвінок (`tel:`),
  поруч Telegram/Viber/WhatsApp з того самого номера, далі решта каналів.
  Колір месенджера — у самому значку, рамка й підкладка нейтральні: п'ять
  різнобарвних рамок змагались з дзвінком. У картці організації ряд той
  самий, що в донорки: кнопка зі словом «Подзвонити» (`primaryLabel`) робила
  його іншим і займала пів рядка — прибрана на прохання власниці продукту.
  Номера текстом немає. Рядок стрічки просить контакти **сам**, щойно
  зʼявився на екрані (`IntersectionObserver` у `ProfileRow` →
  `handleRequestRowContacts` → `readProfileContacts`, точковий
  `profileContacts/{id}`), і лише там, де `canOfferProfileContacts` каже «є
  право» — тобто картка з `feedDate`, власна чернетка чи службовий доступ.
- **Номер у формі доповнення — без пробілів** (`compactPhoneInput` у
  `ProfileCreationWorkspace`): нормалізується і підставлене значення, і база
  порівняння (`buildOverlayPrefill`), тож прибрані пробіли правкою не стають.
- **Посилання Telegram з номера — з «+»** (`telegramFromPhone`): `t.me/380…`
  Telegram читає як юзернейм і відповідає «такого користувача немає».
- **Повернення в стрічку не чекає бекенду.** Підпис кешу стрічки бере роль
  читача через `viewerRoleSignature`: роль приходить то масивом, то рядком
  `'ed,ag'`, і сирий підпис давав різні ключі — кеш не влучав ніколи, а кожне
  «назад» перечитувало `matchingCards`. Поверх того остання дека лежить у
  памʼяті вкладки (`lastFeedSnapshot`, 10 хв, привʼязана до читача) і
  показується на монтуванні одразу; `loadInitial` її не стирає, а тихо
  підміняє тим самим списком.
- **Назва агенції окремо від імені людини** (`agencyName`, вузол
  `profileDetails`): коли в анкеті ще й особиста роль, «Імʼя» й «Прізвище» в
  «Моєму профілі» — людини, а назва організації стоїть першою в анкеті
  агенції/клініки (`roleSectionsFor`). У рядку стрічки вона стоїть над
  програмами (`CardRoleBlock`).
- **Картка стрічки несе копію одного поля анкети** —
  `MATCHING_CARD_MIRRORED_FIELDS` (`agencyName`): значення
  живе й пишеться в `profileDetails`, тож власником поля картка не стає
  (`OWNERSHIP` його пропускає). **Правила під нього треба викотити руками**; доти
  `syncMatchingCardIndex` пише картку без нього (`MATCHING_CARD_PROGRAM_FIELDS`
  — перелік полів, з якими повторюють запис).
- **Усе про волосся — в «Зовнішності» рядка** (`describeHair`: «темне
  хвилясте волосся»), а не ще раз у розділах повної анкети. **Структури
  волосся (`hairStructure`) у картці стрічки немає й не треба**: рядок спершу
  каже колір, а структуру дописує повна анкета, коли відкрили додаткові поля
  чи саму картку. Колір, описаний своїми словами, у словосполучення не
  вставляється — стоїть поруч підписаним («пряме волосся, колір волосся —
  темно русий природній»). Довідник кольору
  тримає іменники жіночого роду («Брюнетка», «Шатенка»), а перед «волоссям»
  стоїть прикметник — словоформи в `utils/profileSentences.js`.
- **Відповіді зі списку в розділах повної анкети — реченням**
  (`describeLooks`, `describeWork`, `describeSizes`): «У мене овальна форма
  обличчя, прямий ніс та повні губи», «Я маю вищу освіту та працюю за
  професією …». Власна відповідь (не з довідника) у речення не лягає — її рід
  і відмінок невідомі, — і лишається рядком «підпис — значення».
- **Бажана винагорода — опис, а не число** (`reward`: текстове поле, `inputUpdateValue` лише чистить пробіли). Тут стояв `formatNumber(value, 9999)`, який лишав самі цифри й обрізав усе понад 9999.
- **Обовʼязковий із контактів лише телефон** (`OPTIONAL_PROFILE_FIELDS` у
  `MyProfile`); винагорода (текстове поле), по батькові й дата циклу теж
  необовʼязкові. Донорці й СМ без ролі організації Twitter, LinkedIn і
  YouTube не пропонуються (TikTok — пропонується: `PERSON_HIDDEN_SOCIAL_FIELDS`). Нові поля анкети донорки й СМ: `fathersname`,
  `lastCycle` (ключ той самий, що в адмінці, вузол `profileWorkflow`) і
  `healthComplications` («Ні» або «Детальніше» з власним текстом,
  `profileDetails`); сімейний стан, куріння й алкоголь мають «Свій варіант».
- **Дотик до контакту — це дія, і рахується кожен** (`recordContactAction`):
  `multiData/contactViews/{читач}/{картка}` = `{ count, lastAt, channels }`
  через `increment()`, тобто запис без читання. Це статистика «чи анкета справді
  цікава», тож показ блоку контактів не рахується, а в підказках значків
  значень немає (`ContactLinks` з `onContactAction`). Шапка форми доповнення
  лічильника не передає, і її підказки називають значення.
- **Стрілка «назад», меню «⋮» і підпис вкладки — у рядку `PrimaryNavigation`**,
  а не в шапці сторінки: сторінка кладе їх туди `usePrimaryNavigationSlot`
  (`PrimaryNavigationSlot.jsx`). Місце під стрілку зарезервоване завжди; вкладка
  карток зветься «Доповнення» / «Чернетка», коли відкрита форма. Меню звідти
  передає `omitPrimaryDestinations` — трьох вкладок навігації воно не
  повторює, — і має хрестик закриття (на телефоні воно на весь екран).
  Сюїти, що рендерять саму сторінку, бачать слот через
  `testUtils/renderWithNavigationSlot`.
- **Контакти показаної картки — спершу з кеша.** Кешована анкета без жодного
  контакту повною не вважається (`getCompleteCachedProfile`): службовий
  `accessLevel` приїжджає після мережевого круга, і на холодному старті анкета
  лягала в кеш без контактів. Але й читати її цілком заради контактів не треба:
  тіло береться з кеша (`getCachedProfileBody`), а з бекенду лише
  `profileContacts/{id}` (`readProfileContacts`, межа до запиту, памʼять таба).
  Так робить `fetchUsersByIds`, а також `ensureFullProfile` для повної анкети,
  яку стрічка вже взяла з кеша. Зібране так назад у кеш не кладеться
  (`isProfileBuiltFromCache`), інакше `cachedAt` продовжив би життя старому тілу.
- **Сурогатна мама без донорської анкети не заповнює донорську**
  (`SURROGATE_HIDDEN_FIELDS` у `MyProfile`): ні зовнішності, ні «чи розглядаєте
  участь у програмі СМ», ні алергій, хронічних захворювань і перенесених операцій
  — 27 полів замість 49. Батьки (лише `ip`) пишуть побажання в
  розділі «Кого шукаєте» (`extraFields`), а не окремим розділом з тією ж назвою, і
  поля «Прізвище» не бачать. Записані значення з анкети не знімаються.
- Плагіни Claude Code для цього репозиторію описані в `.claude/settings.json` разом із
  джерелом (`extraKnownMarketplaces`); перелік і призначення — `docs/claude-code-plugins.md`.
- **Перед нетривіальним завданням — `find-skills`** (`.claude/skills/find-skills`, копія
  `vercel-labs/skills` без змін): спершу гляньте, чи вже встановлений skill покриває
  задачу, а якщо ні — пошукайте в екосистемі. Три застереження, бо skill писався під
  локальну машину:
  - у веб-сесії `skills.sh` закритий політикою мережі, і `npx skills find` на відмову
    відповідає **«No skills found»** — це не «такого skill немає», а «не спитали». Доки
    домен не дозволено в налаштуваннях середовища, шукайте по GitHub (`raw.githubusercontent.com`
    відкритий) або кажіть людині прямо, що пошук недоступний;
  - `-g` з інструкції skill у контейнері нічого не дає — його стирають разом із сесією.
    Ставте в `.claude/skills/<назва>/` і комітьте;
  - чужий skill — це чужі інструкції агентові. Перш ніж ставити, прочитайте `SKILL.md`
    цілком і спитайте людину; домовленості цього файлу він не перебиває.
- Частина цих домовленостей продубльована машинно: `.claude/hookify.*.local.md` —
  правила, що спрацьовують на самій правці (`database.rules.json` без емулятора,
  `get` на `users/...`, поле картки поза схемою, пуш у `main`). Комітяться навмисно,
  попри пораду плагіна їх ігнорувати: інакше вони не діють у веб-сесії.
